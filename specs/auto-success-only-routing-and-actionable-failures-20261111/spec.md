# 自动路由成功优先 +「运行与积压」原流程恢复

**Status:** Owner-approved (owner-delegated Spec Review of f1b406f9ff7b97ee8ad60ec933fc41a0670ed3b2)
**Target:** develop / VM13 preview, not main. 用户明确批准本功能，包括从可用的付费模型池路由与自动重试。

## 用户规则
- **成功只有一种**：模型返回通过当前流程业务/结构校验的可用结果。HTTP 200、原始 receipt received 但 JSON 无效或摘要超限均不算成功。其他所有**已结束**的尝试均视为失败，不再分 429/超时/JSON/计费/unknown 决定是否切换。尚在发送的 pending 保持「处理中」直到有结论。
- 自动路由在启用、允许路由、有凭证且匹配文本/视觉及轻量/标准/高级等级的**全部**模型实例之间切换；不按免费/付费筛选、不隐式降级到低于所需等级。同名不同供应商账户以注册模型 ID 区分。固定手工绑定不应偷偷变为 auto。
- 当前实例未得到合格答案时，记录原错误与原始回执，然后本次操作**立即换下一个模型 ID**，一个操作内每实例最多尝试一次；从最后实际成功的实例优先选。后续请求不能在 1 小时后继续优先选失败模型：失败状态需要跨 Worker 进程可见并至少覆盖 UTC 当日，后台「刷新模型」可清除失效状态让恢复后的实例再次参与。若所有当前可用候选都失败，**真实失败/待恢复**，不可报成功，不得无限循环；现有任务恢复处理后续重试。保留实际调用及费用可审计信息，但**不要求人工核对供应商是否计费**才切换或重新执行。内部 receipt 可保留「结果未知」原始证据，只是不把它当作用户操作门槛。
- 只做正常工作流的路由/恢复，保持 shutdown 中止、在途并发保护、真实凭证权限、现有预算阀门和已持久化答案复用；不添加定时器、新模型表、软删除或额外的工作流。

## 「运行与积压」检查出的现有问题
1. **重复/误导计数**：一个新闻可出现 `article:`、`job:`、`model:` 多行。「失败」包含一次业务的多个失败回执，界面没标出执行单位，用户把 6 次失败误认为 6 篇新闻。按**待处理/处理中/失败**展示唯一原执行任务（新闻 ID+流程，独立定时任务/Worker 同样按唯一原任务），成功/重试中的原任务不再以旧模型失败重复占据失败队列；旧 attempts 仍能用于诊断。顶部失败数、筛选后的总数、分页和导航角标用同一个函数/口径。
2. **错误状态**：`unknown` 模型结果当前被映射 `pending`，实际无法自动继续；业务回执已 `received` 但后续结构校验失败时 `receipt_attempts` 仍显示 `received`，路由成功率虚高。应以**业务校验通过且任务完成**为成功；未知已结束请求应显示失败且可恢复，不再显示「核对回执」或者要求填写计费状态。
3. **无效操作**：模型行只显示「由原任务恢复」静态文字、无法点。每条失败必须显示：**所属新闻**（能关联时链接到新闻详情，系统/事件任务显示准确所属对象而非虚构新闻）、**失败流程**（人能读懂的名称）、**原任务当前真实状态**（待处理/处理中/失败/已完成，以及当前队列或回执）、**实际可执行的「重新执行该流程」**。从现有 `/api/admin/content/:id/rerun`（extract/analyze/group）、已有 jobs/schedule retry 复用恢复路径，增加缺失的英文内容单条重跑/其他必要的原流程入口；不能把 `english_copy` 错重跑成完整新闻分析。若历史 Graphiti 只有不可逆短 hash，无法可靠找回原文章/输入，就明确「无法定位原任务」并链接到可操作的 Graphiti 流程级恢复，不可假装重试成功。
4. **重复重试/竞态**：点击前后必须二次检查任务状态；完成/处理中/已重入队的任务不可重复发送，复用 `Idempotency-Key` 和现有审计。对 unknown 用新的请求身份/模型实例执行，不重发原未知请求；清除人工核对阻断。操作成功后返回确实创建的 job ID / 排队状态，自动刷新列表；操作失败保留错误和原因。
5. **移动端与长文本**：目前表格内容自动撑宽，操作列在最右端不易触达；原始 Graphiti hash、长模型名和错误文本难读。合理限宽/缩略、点击或 title 展示完整信息；手机 390px 核心操作可见且可点，允许详细错误区横向/纵向滚动。坚持复用 `DataTable` 和现有控件，不重写通用表格。
6. **日期与分类**：只看 UTC 今日业务执行/关联的新修订，不让昨天未变化的失败长期混入当日；`blocked` 预筛拦截不是失败新闻（如已正常判定 BLOCK）。正常待处理和真正处理中不能当失败。非新闻任务（采集/定时任务/消息投递）保留来源、状态、合适操作，不把系统任务显示为一篇新闻。分页显示真实总数、可选当前页批量重试**在有可恢复对象时**复用同一个后端命令，按原任务去重，逐条返回结果、不能单个失败阻断其余。

## 验收标准
1. 单个工作流模拟两模型：首个返回无效 JSON、超长字段、400、429、HTTP 200 空内容、超时/unknown 任一种，第二个提供合格输出，业务应当完成且实际使用第二个模型 ID；原失败留下可诊断 receipt；不能把失败的 raw received 算为成功。不同供应商账号、免费与付费候选都参与；固定绑定保持固定；不能无限调用。
2. 模型失败后在不同 worker 进程的下一次选择排除失败实例，直到明确清除/次日复位；再次成功的实例可重新成为首选。任何失败没有成功时正确反映真实失败，避免已完成新闻在失败队列仍出现旧模型记录。
3. 今天 UTC 一条新闻的原始模型/Worker/新闻多条失败不会产生多个可重试任务、计数一致。对同一文章两个流程失败，可明确显示阶段和最新状态；历史错误可查但不算活动故障。归组、英语副本重跑必须只触发对应步骤；Graphiti 无法映射输入时不伪造具体文章，提供明确的处理限制。
4. 同一行点击「重新执行该流程」成功会真实入队（或向已有对应作业提交）并从失败变成待处理/处理中；并发或再次点击不创建重复任务。Unknown 失败无需费用人工核对步骤。不可重放对象说明真实原因而不是死按钮。
5. 手机 390 px 与桌面 1440 px：无页面级横向溢出、失败行能识别新闻/阶段/原任务状态，操作可触达，长模型/错误有完整查看途径；分页 20 项实际有总数，保持可筛选，批量重试若实现需去重、部分成功反馈。
6. Spec 审核通过后实现 PR 引用合并至 develop 的 Spec SHA；单元/后端/Web 浏览器/E2E/独立审核/合并自动发布 VM13。在线验收含真实 Admin 登录后运行与积压交互，不触碰 VM09，不自动合并 main。

## 边界
保留错误日志、审计、原始计费/用量数据（没有人工核对义务不等于擦除事实）。不删除已有新闻或回执，不调整付费供应商凭证或预算，不在本变更中新建模型或数据库迁移。
