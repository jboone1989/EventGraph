# Feature Specification: 值得看 · Ferro 内容价值发现实验

**Feature Branch:** spec/worth-your-time-experiment-20261106  
**Created:** 2026-11-06  
**Status:** Draft — revised after owner feedback; requires fresh Spec Review  
**Target:** develop  
**Input:** 将「值得看 / Worth Your Time」作为 EventGraph 实验栏目，但不要再造一套推荐系统。内容价值发现、独立判断与持续研究属于 Ferro 的职责；EventGraph 是独立的公共事实基础设施，不应把 Ferro 的认知逻辑移进新闻 worker。

## 1. Problem and hypothesis

很多作品（包括 AI 作品）只改善了形式，却未必给观看者带来值得投入时间的情感、认知、审美、幽默或实用体验。用户不排斥 AI 内容，排斥的是缺少实际体验价值、却消耗注意力的内容。

实验问题不是「哪些内容更容易被点击？」或「每天推荐哪五条？」，而是：

> Ferro 能否主动发现被流量逻辑忽视、却可能让人看完后觉得值得的作品，说明它判断的依据，并在真实反馈中学会辨别自己的误判？

**这不是个性化推荐产品。** 不预测个人兴趣，不构建用户画像、兴趣标签、内容分数、排序策略，也不以日更频率或条数作为目标。先验证 Ferro 的发现和判断能力是否存在。

## 2. Responsibilities — hard boundary

| Component | Owns | Does not own |
|---|---|---|
| **Ferro** (independent Content / Research Agent) | 在自身执行环境中主动寻找外部作品；选择研究对象；实际接触可用素材并形成带证据的内容价值判断；记录不确定性、失败和迭代；决定何时提出一个发现 | 不代替 EventGraph 的公共新闻事实层；不把个人观点声明为已证实事实 |
| **EventGraph** (public knowledge and presentation infrastructure) | 提供已有公开事实/事件/API/MCP 作为可选研究材料；展示 Ferro 或其他明确署名作者提交的实验案例、原始链接和判断依据；保存反馈与可核实实验结果 | **不在自己的 worker 里运行“高价值内容”模型评审；不自动全网搜视频；不建 Ferro 副本、个性化推荐器或另一套 Agent loop** |
| **Human visitors** | 阅读原作品、自愿反馈是否值得、指出具体误判 | 不被视为统一的偏好函数；反馈不证明所有人都喜欢同一内容 |

Ferro 是首个实验主体，不把公共接口写死为 Ferro 专用 API；以后其他 Agent/人类作者也能明确署名提交。**不要求将 Ferro 的身份、记忆、目标或工作循环复制进 EventGraph。**

## 3. User Scenarios & Testing

### User Story 1 — 看到可检验的发现案例（P1）

访问 `/worth` 或 `/en/worth` 时，读者看到的是 Ferro 的**发现实验记录**，而不是按热门程度或 AI 数值评分排序的推荐信息流。每个公开案例明确显示：原作品标题与作者/来源、真实原文地址、内容媒介、Ferro 的判断与具体理由、它依据什么材料作判断、有什么不确定性。允许 AI 作品，也允许普通人作品，不因创作方式决定价值。若材料没有实际被查看/读取，应明确「仅根据标题/摘要的初步发现」，不得冒充看完视频后的审美判断。

**Independent Test:** 以一条有可核对素材的短片案例、一条只有摘要的案例、一个隐藏案例及一个空库运行双语页面与 API。

**Acceptance Scenarios:**
1. Given 有已经发布的案例，When 访客打开栏目，Then 看到来源、证据范围、判断理由与原作品链接，不显示捏造的观看时长、热度分数或 AI 质量分。
2. Given 只获得标题/文字简介，When 发布案例，Then 必须标注判断范围受限，不得声称已经体验作品的情绪或镜头表现。
3. Given 没有通过验证的发现，When 访客打开栏目，Then 展示暂无实验案例，而不是每天凑 5 条。
4. Given 来源已经撤下或编辑撤回案例，When 公开查询，Then 不再展示被撤回记录；后台保留可审计的更改历史。

### User Story 2 — Ferro 独立提交发现和反例（P1）

Ferro 在自己的运行时通过既有工具发现并研究作品；经一个**来源中立**的受控发布边界，把结构化的「发现记录」提交到 EventGraph。EventGraph 不触发 Ferro 的发现，也不再次调用模型复核价值。允许提交「我起初认为值得，但人类反馈并不认可」的反例；不要只展示成功故事。

**Independent Test:** 使用模拟 Ferro 发布方，提交合法/不合法、重复和被撤回的实验记录，并证明新闻 worker/发布链路不受影响。

**Acceptance Scenarios:**
1. Given Ferro 提供真实 URL、来源及研究证据，When 通过既有管理/作者受控入口提交，Then 同一个原始作品在同一实验案例中幂等更新，而非重复生成卡片。
2. Given Ferro 对同一作品改判，When 提交新版本，Then 保留前次判断、发生变化的理由和时间，不抹去失败历史。
3. Given Ferro 不可用或未进行探索，When 新闻照常发布，Then EventGraph 新闻分析、事件分组及日报完全独立正常运行。
4. Given 任意外部 Agent 提交，When 无权限或格式无效，Then 不会公开记录；无需为 Ferro 新增独立密钥服务或第二个发布系统。

### User Story 3 — 验证是否“值得”与“发现了新东西”（P2）

用户可以在打开原作品之后选择「值得 / 一般 / 浪费时间」，并可选回答「以前是否知道这部作品」。每个案例展示反馈样本和相互矛盾的感受，不把少量观众的投票变成客观艺术评分。实验能查看 Ferro 选中的案例与同题材、同媒介、同时间段的一组常规热门内容（人工固定基线）的差异，防止只挑爆款却误以为自己有发现能力。

**Independent Test:** 使用固定样本和无/有反馈的案例，验证统计分母、匿名会话去重、反例展示、基线可追溯。

## 4. Functional Requirements

- **FR-001 — 定位：** 栏目名「值得看 / Worth Your Time · 实验」，页面首屏说明它展示 Ferro 的内容发现与价值判断实验，**不是每天固定更新的个人推荐信息流**。
- **FR-002 — 案例形式：** 一条案例必须包含原作 URL、来源/作者（如可核实）、媒体类型、可用材料的范围（实际观看/阅读、片段、描述或仅标题）、Ferro 的判断及具体依据、已知限制、发现时间、署名、版本。不要自动抓取或转载外部作品全文；没有可访问素材不得伪装为完整审阅。
- **FR-003 — 不设日更指标：** Ferro 自主决定探索和提交时机；EventGraph 按案例/时间归档，不设每日 5 条、30 候选、单批打分、定时策展、质量分数或强制排名。没有新案例是正常状态。
- **FR-004 — Ferro 能力边界：** 寻找候选、研究材料、提出价值判断、对比可能的反例、反思和修正都在 Ferro 自身系统完成。**EventGraph 内不新增 LLM 调用、策展 Prompt、自动轮询或模型绑定。** 不在本仓库构建第二套通用 Agent Runtime。若 Ferro 现有工具暂不支持某媒介，实验明确记录限制，不虚构已经完成评审。
- **FR-005 — 独立中立的投稿/读取边界：** 优先复用现有 `modules/research` 的作者稿件、管理员保存/发布与公共读取模式（研究模块已经有受控写入）。在无法无损容纳结构化案例时，只增加最小类型与存储/API；发布入口必须鉴权，保留作者署名、来源、审计与撤回。不得把投稿塞进普通新闻 ingest 以改变新闻流。
- **FR-006 — 事实和判断分离：** 原始作者、作品内容/出处为可核实材料；「值得」与「可能感动」是 Ferro 的判断而非事实，清晰展示不确定性与证据。保留改变看法的历史版本；不因模型自信而提高证据级别。
- **FR-007 — 反馈：** 公开三档「值得 / 一般 / 浪费时间」反馈与可选「此前已知道 / 不知道」；使用现有匿名 session、同源请求和限流模式，一个会话对同一个案例保留一条当前反馈，可修改，不做账号、兴趣画像或个性化召回。
- **FR-008 — 可验证比较：** 小规模实验使用预先记录的常规热门内容基线（原始来源与选取规则可追溯），避免用 Ferro 自己选的案例同时充当对照。按媒介/主题/时间尽可能可比，结果标注样本数和选择偏差。最重要的指标是「未知作品中的值得率」与误判/反例，不是 CTR 或停留时间。
- **FR-009 — 展示和导航：** `/worth`、`/en/worth` 两种语言版本，桌面 More 与手机「我的」入口，响应式内容页面，无无限滚动。未提供可靠译文时清楚标注原语言，不能编造翻译或不同语言的判断。
- **FR-010 — 低耦合：** Ferro 失联、未知模型成本、投稿失败或没有案例时，EventGraph 新闻采集、统一分析、新闻详情、事件归组、日报、Hero 和热榜完全正常；用户打开栏目不调用模型。
- **FR-011 — 不虚构集成已完成：** 仅有 EventGraph 接收端与模拟投稿测试，不等于 Ferro 已具备真实材料阅读和投稿能力；真正的 Ferro 端探索/研究/投递必须在其独立项目验证，并留有一条可追溯的真实端到端案例，才宣称实验上线。
- **FR-012 — 反馈回路归属：** EventGraph 只保留匿名汇总与案例级反馈，Ferro 可经授权的读取接口获得**聚合反馈**以自行复盘；不允许 EventGraph 代 Ferro 更新目标、记忆或决策策略，也不把匿名 session 交给 Ferro。

## 5. Entities

- **DiscoveryCase:** case ID、作者/Agent 身份、原始作品 URL、出处/媒介、可用素材范围、Ferro 的具体理由与证据、限制/不确定性、状态、时间；可以关联 EventGraph 已有 item/story，但不要求只来自新闻。
- **CaseRevision:** 原始判断、改判内容、时间与说明，可查阅以便观察误判。
- **CaseFeedback:** case ID、匿名会话标识、三档反馈、此前是否知道该作品（可空）、是否从本站打开过原文、更新时间；在 EventGraph 内聚合展示，不对外泄露会话标识。
- **ComparisonSample:** 手工记录的对照作品 ID、选取规则、来源、主题/媒介/时间、实验批次；不使用第二套推荐引擎。

## 6. Success Criteria

- **SC-001:** 公开页面不是每日推荐列表；零条/一条/多条案例均正常，有原始来源、判断材料范围、清楚的 Ferro 作者归属和可检查理由。
- **SC-002:** 真实 Ferro 端到端演示至少提交一条来源可核对的外部作品案例，并能解释它实际获得了什么材料、无法判断什么；未验证前只报告「接收端完成」而非「Ferro 自动发现已上线」。
- **SC-003:** 预设一小组同媒介/主题的常规热门案例作为可追溯对照，持续观察至少 14 天，记录每组有效反馈、此前未见比例、被认为值得的比例和典型失败。
- **SC-004:** 样本少于 30 条有效反馈时只做探索性描述；不能宣称超过推荐平台、已经具有审美判断能力或统计显著性。
- **SC-005:** Ferro 宕机与投稿失败不会阻塞任何既有新闻处理；用户打开栏目没有模型调用；权限、撤回、重复案例与反馈去重有独立测试。
- **SC-006:** 逐案例展示 Ferro 的判断如何随人类反馈被修正（允许「未修正」和「不同意反馈」），不把所有分歧自动收敛为一个用户偏好分数。

## 7. Explicit non-goals

- **不做** EventGraph 每天运行的 AI 推荐、模型评分、个性化信息流、点击率优化、热度排行榜、重新采集全网视频、生成 AI 作品、由站点自动修正 Ferro 的认知。
- **不做** 新 Agent 平台、Ferro 镜像进程、新模型配置/Provider 模块、独立 GitHub 定时器、对现有新闻发布链路的任何改变。
- **不做** Ferro 的通用能力开发（由 Ferro 自身仓库/工作流独立承担；不能把它伪装成 EventGraph GH-AW Work Item）。
- 与 EventGraph 的原创内容分发栏目「每天看看世界又整了什么活」独立，不互相阻塞。
- 只针对 develop 实验；main/生产遵循现有发布流程。
