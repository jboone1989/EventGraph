# EventGraph · 跨 Story 演化阅读实验 Spec v0.1

> **状态：DRAFT，等待用户审定验收条件；尚未实施、部署或验收。**
> 2026-10-26 已确认的方向：保留首页与新闻获客，使用现有探索工作台试验跨 Story 的持续过程和变化。技术研究见 [research.md](research.md)，不得绕过 Search Before Build。
> 这是一场验证读者理解能力的**小实验**，不是全站 EventTree/Graph 重构，不是发布自动因果推断的授权。

## 1. 要解决的问题

现在报道会被归到同一发生（fact）和直接发展（story），时间回放也只覆盖一个 Story；读者难以看到两个独立 Story 在更长期间里发生的联系、共同影响或演化认识。系统不能因为两个 Story 同时提及某个实体或发生在相近日期，就断言其中之一导致另一件事。

成功不等于可视化好看，而是读者能更准确回答：「哪些事实分别发生」「哪些状态可核实地改变」「哪些联系确有来源」「当时已知什么，事后才知道什么」。

## 2. 参与者与入口

- 研究用例由开发/编辑人工准备，至少 **1 例含 2–3 个原本独立的公开 Story**；选题须能查到证据，不能凭页面效果虚构交汇。
- 首轮在已有 `/explore` 中用可识别的 `?case=<case-id>` 模式呈现；原有 `?story=` 和 `?entity=` 功能保持，中文和英文入口的行为一致。
- `/` 首页、`/hot` 热度榜（现有“事件树”入口）、`/items/:id`、`/story/:id` 的 SEO/canonical/内容布局**不变**。实验链接不放主导航、不进 sitemap、noindex。
- 不要求注册、登录、订阅、不改变生产配置；是否进入正式可索引站点须另行批准。

## 3. 可验证要求

| ID | 验收条件 |
| --- | --- |
| FR-01 | 给定真实案例时，展示至少两条具有稳定 Story 公共 ID 的独立轨道，轨道站点来自现有公开 StoryRoute/Fact/来源，点击能进入原 `/explore?story=` 或公开新闻原文；任意已撤回或不可公开的站点不得展示。 |
| FR-02 | 共享一个明确时点的视图。区分来源发布/本站首次获知与事实发生/生效，未知时间不猜；历史模式说明是有界重建。 |
| FR-03 | 跨 Story 联系必须人工标注其类型、方向（如确有）、来源 URL、署名/机构、来源发布时间和策展/解释时间；只能呈现可核查的「响应/明确引用/客观依赖/来源声称」等，不将时间临近或实体共现变成因果。 |
| FR-04 | 如果没有足够公开证据，不画跨线连接；有争议的说法展示归属与不确定性而非定论；后来才提出的解释不能出现在此前的「当时已知」视角。 |
| FR-05 | 复用现有出版公开过滤层、时间处理方式、StoryRoute 和知识图谱组件。不得在首轮创建新图数据库、RAG/embedding 管道、独立搜索、故事归组或登录系统；阅读交互不发 LLM 请求。 |
| FR-06 | 在桌面和约 390px 移动视口均能区分不同轨道、点击来源、不产生横向失控或误把交汇当因果箭头；中文和英文文案、时间含义一致。 |
| FR-07 | 带案例参数的实验页面不纳入索引或 sitemap，旧首页、新闻详情、原有工作台和热点榜维持原来的导航与语义。 |
| FR-08 | 使用同一组真实来源制作对照：普通单线时间列表、候选多轨态势线和现有图谱视角。记录答题准确率、证据核查正确率、无证据因果误判率和读者完成时间；先定度量和样本再评价。 |

## 4. 实验资料与技术复用

- 人工案例数据首先以**少量可审查的仓库内容**存在（可参照 `site/topic-briefs.ts`），引用既有 publicId 和原始出处；不复制文章正文，不预建新表。
- 后端仅使用 `packages/backend/src/publication/` 已有查询和公开过滤条件组装案例；不让前端用 case 配置直接呈现未经公开过滤的内部内容。
- UI 先测试最小分组时间展示，不为 2–3 条线引入库。已有 Cytoscape 仍负责实体关系。真正需要多尺度缩放、密集站点排布后先评估 [vis-timeline](https://github.com/visjs/vis-timeline)，禁止自己扩建通用时间轴库。
- 不把 EventKG、NewsLines 等研究原型引入运行时；仅借鉴其有出处的事件组织和阅读设计。参见 [research.md](research.md)。

## 5. 明确不做

- 改首页、修改 EventTree `/hot` 的热点含义、批量重写新闻页 SEO、建立新的顶层研究站点。
- 自动推断跨 Story 因果、预测战争或资产价格、无证据地生成状态变量。
- 把两个不同 Story 合并为一个 Story，或者给每个新报道强制找到长期“态势”。
- 重建 Graphiti/Neo4j、重复写时间回放、开发第二套编辑 CMS、为了演示就加模型服务。
- 用人工策展原型的通过率冒充自动发现能力；未来自动候选召回与错误率需独立 Spec/评测。

## 6. 放行与否决

最先做**数据存在性核验**：找不到 1 组具有真实、可公开、不同 Story 的关联实例及证据，就先停在研究，不编示例。若数据满足，再以真实原文做只读实验。

产品实验必须特别检查：多轨版是否提高读者正确理解，且**没有增加错误的因果联想**。若只是让图更复杂或让用户更相信无证据连接，即使视觉吸引人也不扩展。先给用户/独立 Opus 看可核查的事实样本和验收记录，再由用户决定长期过程数据模型、自动发现、独立网址和正式发布。

本草案应作为独立 Spec 通过用户批准后方可进行实现 PR；仅记录方向的聊天许可不能代替对具体字段、验收和真实样本的确认。
