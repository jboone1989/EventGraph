## 1. 真实问题与证据（2026-10-26）

**可重现样本**：VM13 开发预览 `http://43.133.185.154/story/93a28e20-4a3b-4f3e-89ee-e07deb8897ea`，主题为 OKX-ICE 代币化股票计划发行人异议。**这是页面当时返回的数据与 UI 观察，不是我们再次核实过的外部经济/政策事实。** 该 Story 共 **11 篇公开报道、3 个来源**。页面的实际显示包括：
- 顶部事件综述 + 最新进展；
- 嵌入的 `EventExplorer`：时间回放、按时点的 **11 条事件进展**、11 篇已知来源，以及图谱/影响分类；
- `StoryRoutePanel`：**11 个逐站节点**，其中大量内容仍是“9/16/22 家公司提出异议”的媒体改写，几乎每站“单一来源”；
- “完整来源索引”再次列前几篇报道及摘要；
- “报道时间线”再列全部 11 篇报道和摘要；
- “官方一手”若为空，部分视图仍占位显示零条线索或解释文本。
同一批文章被多个板块重复展示；**同一数量的报道 ≠ 同一数量的独立演化阶段**。初步可读主线是异议主体数量从 9 → 16 → 22（以站内当时报道为据）、平台方公开回应是另一个不同发展；不能为了凑成“3–4 站”合并所有不同时间和法律效力的事实。

**代码核对**：
- `apps/web/app/routes/story.tsx` 同时渲染 `EventExplorer`、`StoryRoutePanel`、“完整来源索引”、`TimelineRow` 报道时间线及侧栏官方报道；
- `apps/web/app/features/story/EventExplorer.tsx` 又渲染 `EventTimeMachine`、`developmentsAt` 列表及来源/影响区域；
- `packages/backend/src/publication/story-route.ts` 以 **Fact（f.id）** 作为站点，事实中的报道作为各站证据；
- `packages/backend/src/publication/stories.ts` 已有按 Fact 归组的 `developments`；`packages/backend/src/events/{group,relate}.ts` 已有 SAME_OCCURRENCE / SAME_STORY 规则及人工更正，不能绕过。

**关键待证实判断**：样本出现 11 个 Fact 站点并不单凭此就能断言数据库错误，可能不同公司的独立提交/不同日期具有真正不同的事实身份。必须检查每个 Fact 所含实际发生行为、时间和原文，才可以判定过度拆分与误分并合并的代价。

## 2. 产品边界

- **必须保留**：`/hot` 热点榜现有定位、`/story/:publicId` 稳定 URL/SSR/canonical/结构化数据/索引规则，以及 `/items/:id` 独立新闻 SEO。首页绝不因此改版。
- Story 详情首先是**面向普通读者的连续事件档案**，不同于研究者的图谱调试控制台。优先读懂「发生什么、为何重要、真正改变了什么、下一步有什么已确认的信息值得留意」，而非一次性展开所有可用内部组件。
- 所有原文、纠错证据与公开报道保持可访问；**减少重复展示不等于删报道、撤稿或重写历史**。独立的 `/explore?story=` 承担完整时间机器/图谱/按时点证据，不需要第二个工作台。
- 用户本轮只批准“加入规划并让 Claude 看”，**并未授权直接调整生产或自动批量合并 Fact**。

## 3. 建议的信息层级（等待 Opus 评审后审定）

1. **一眼读懂**：保留当前综述、核心事实/已确认变化、最新独立进展，并与新闻解释层 5W1H + So What + What Next 衔接。不要同时重复摘要与最新一句话中的完全相同信息。
2. **关键演化节点**：从已有 Fact/StoryRoute 中提炼少量*真正发生了变化*的阶段，作为唯一面向普通读者的事件路线；每阶段展示变化及证据数/来源链接。将不同媒体对同一阶段的重复报道折入节点下的证据，不能抹去实际不同决策/异议/更正。
3. **完整报道证据**：只保留一处完整、可筛选的报道时间线（按最新/最早、官方/全部）。已有完整来源索引与右栏官方全文列表若无额外证据价值，则移除或改成筛选快捷入口，而不是复制全文。
4. **深入研究入口**：默认不在 Story 页整个嵌入 `EventExplorer`，改成指向既有 `/explore?story=` 的明确链接/轻量入口。时间机、实体关系、各时点来源及影响调查仍在那里可用。
5. **空证据状态**：没有影响资料/市场时间序列时不展示四个空白分类；必要的不确定性提示放在相关事实/节点附近，不能误导为“没有影响”。
6. 热度图、相关主题/事件和适量上下文可保留，但不应与核心阅读流重复已有内容。桌面与约 390px 手机应同样符合阅读层次。

## 4. 必须先完成的 Fact 归组诊断（先查再改）

- 只读核对样本 11 条 StoryRoute stations 的 `factId`、每站 `articleId`、`occurredAt`/有效时间、原文 URL、报道的实际行为/主体、已有人工归属/合并/更正记录；**记录可复现证据**而不是仅靠标题相似。
- 手工标注 `SAME_OCCURRENCE`（同一次真实发生）、`SAME_STORY`（同一长期事件的不同真实发展）、仅重复媒体表述，以及证据不足。比较已有模型归组决策/候选检索是否存在漏召回、模型分类失误、来源不同所致的重复或故意保守拆分。
- **不提前设定目标节点数**。从 11 Fact 中核查出的真实独立变化可能是 3、4 或更多；必须保留来源独立性和有意义的不同发生/企业立场。
- 首轮不批量重跑历史、不训练/替换 grouping 模型、不加新模型验证层；如果诊断证实归组错误，再提出现有人工纠正或具体最小算法修复，独立评审且保留重定向与原文追溯。
- 如事实本来就独立但信息上构成相同“阶段”，**允许仅在展示层做编辑级聚合**，不得为美化 UI 改写 Fact 身份。

## 5. 可验收行为（仅建议，未批准实施）

| ID | 可验证结果 |
| --- | --- |
| SD-01 | 同一个 `articleId` 不在普通读者默认 Story 页面作为多个完整新闻列表条目重复出现；用户仍能在唯一完整报道时间线中找到全部 11 篇公开报道和原文 URL。 |
| SD-02 | Story 概览、关键节点、证据时间线彼此职责明确；没有第二个内嵌完整时间回放/证据列表，独立 `/explore?story=` 正常可达且内容不缩水。 |
| SD-03 | 关键阶段表达的是事实或可核实状态变化；不同来源的同一事件说法归在阶段的证据下；如果需合并 Fact，要提交逐条原文比对与更正/重定向验证，不凭数量或标题决定。 |
| SD-04 | 无影响线索、无市场快照、无官方来源时不堆 0 条卡片；无证据不推断无影响或无官方立场。 |
| SD-05 | 详情页 `/story` 及中英文版本的 SEO/canonical、来源权益、旧锚点/跳转、移动端、原有热度与新闻完整性不倒退；可用真实浏览器对照检查重复块、页面高度/加载速度和有效二跳。 |
| SD-06 | 基于至少当前案例 + 一例不同领域较复杂的事件验证：对照阅读理解、证据可达性、重要阶段遗漏率、错误“同一事实”合并率和页面交互，不把页面短等同于读者理解改善。 |

## 6. Search Before Build / 最小范围

优先复用：`story.tsx` 的 `Panel/TimelineRow`、已有 `EventExplorer` 独立 `/explore`、`StoryRoute`、`developments` 和 `group/relate` 的现有事实判断 + 人工修正能力。不新建第二套时间线、React Flow、通用去重服务、图模型或评论系统。

独立 Opus **先回答这些反方问题**：
1. “删完整来源索引”和“去掉内嵌 Explorer”是否会让本来有价值的证据横向核对变得不便？有没有更小的折叠/单一数据源实现？
2. 当多个不同事实描述同一次更大进展时，应该修改 Fact 的归组还是只在视图层编辑阶段？具体在哪些边界最容易误合并？
3. 5W1H + So What + What Next 适用于每一条新闻还是 Story 概览？怎样避免又新增 3 个重复板块？
4. 这会不会损害现有深读指标、站内搜索转化或 SEO，怎样最小实验验证？

**现状**：只建立规划/独立评审任务，未改动页面或数据库。
