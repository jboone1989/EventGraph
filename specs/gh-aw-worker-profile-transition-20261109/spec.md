# GH-AW Worker contract-safe admission after compatible deployment

**Status:** Owner-approved (owner-delegated Spec Review of b3e1f50dd8729ccbfd182ff6e5a85817a4ceaf1e)
**Scope:** Existing GitHub-native GH-AW Producer contract binding and regression tests; no new Worker, no queue migration.
**Incident:** The approved Spec #529 merged at `develop@874078a95e44b3c84791a36279f46a39a65550cf`. Native Producer created existing Issue #530 and then failed `submit-graph` in [run 42614406063](https://github.com/jboone1989/EventGraph/actions/runs/42614406063): `work_invalid: node identity/profile/trust/account mismatch`.

## Reproduced source-level root cause
- The queue Policy's installed `default/eventgraph-worker` identity starts with logical contract `665e9e00...`. After adding official `network.allowed: node` to its allowed egress, GH-AW's verified `deploy --from-config` recorded a **current** immutable Worker revision at `main@fa08c36799638c8d6456a679183361088d8fed3d`, logical contract `25471841...`, same workflow, trust domain `default`, credential/effect scope, principal, max claims and key sharing as the previously installed Policy. The deploy was allowed by the native `deploymentBoundary` check; it is a **compatible scope/identity upgrade** under GH-AW v1.0.1.
- The Producer's `defaultWorkerRoute()` validates current deployment availability but returns **the old Policy profile**. `buildWorkGraph()` then embeds its stale `logical_contract` into every new Work. In pinned official GH-AW v1.0.1 source, `pkg/workqueue/deployment.go` `admissionProfile()` chooses the current immutable deployment revision when `ExecutionRef` is absent, and explicitly rejects a non-empty `Work.LogicalContract` that disagrees with this current revision. `pkg/workqueue/graph.go` `admitWork()` then reports the generic `work_invalid` shown in the incident.
- GH-AW's native `admitWork` **persists the actual chosen immutable revision's contract as `WorkState.AdmissionContract`**. The optional submitted `Work.LogicalContract` is a pin, not required for safely binding the verified active revision. Omitting that pin never skips trust, identity, Work ID, entitlement, effect-scope, profile or actual deployment validation.

## Exact minimal change
1. **Use GH-AW native active-revision resolution.** For newly generated eligible Spec Work without an explicit owner-approved immutable execution pin, leave `Work.LogicalContract` and `Work.ExecutionRef` **absent**. Keep `worker_profile` equal to the existing installed Policy `default_profile`, `pool` as `default`, `batch_trust_domain` from that installed Policy, canonical Work ID, Issue/Task/Spec immutable provenance, fairness metadata, resource and effect contracts unchanged. Native `submit-graph` then selects the current independently verified Worker revision and stamps its exact contract into authoritative Work state. Do **not** substitute an unverified contract string, monkeypatch GH-AW CLI or bypass its admission guard.
2. **Fail closed before submission.** The Producer must verify an AW Policy with an installed default Worker profile, exact same-repo pool, current deployment ref and contract, and a `revision.available=true` current revision. If the current registered revision's trust domain or identity/scope boundary differs from installed profile, if revision metadata is missing, or if the Worker is unavailable, fail with a specific actionable error. A genuinely incompatible change must be escalated for versioned profile or quiescent Policy update; do **not** silently accept it.
3. **Preserve existing queue and work.** Do not edit `work-queue` branch/ledger, reset the Policy epoch, clear/cancel Work, register a duplicate Worker, create a second queue, manually alter #530, mint synthetic Result, or dispatch unapproved duplicate Worker runs. Existing already-admitted Work stays bound to its original immutable contract; the change applies only to new Work.
4. **One-time non-agent bootstrap only.** The native queue cannot dispatch a Worker to repair its own admission. After this **lightweight Spec** is independently reviewed, stamped Owner-approved and normally merged to develop, use one ordinary non-`agent-work` feature PR to update the **existing** `scripts/ci/spec-task-producer.mjs` and focused tests. Keep original Check/Docker/E2E/independent code-review gates and automatic develop merge; activate on default branch via the existing guarded `develop -> main` merge only, without direct push.
5. **Restore the original business Work.** Once the code is active in the default-branch workflow, re-run the existing native successful-develop-Check admission path for exact `develop` HEAD; it must reuse Issue #530 and its original immutable approved Spec `specs/prod-hot-ranking-release-gate-20261109/spec.md@874078a95e44b3c84791a36279f46a39a65550cf`. Confirm a genuine native `Work` record with its pinned active deployment's `AdmissionContract`. Preserve queue/PR serialization; only native dispatch may start the Worker. A successful replay/issue creation alone is not successful implementation.
6. No production modifications, changes to `EVENTGRAPH_PROD_AUTO_DEPLOY`, VM09 SSH, business hot-ranking behavior, migrations, model billing or schedule. The approved #529 Work itself will implement the separate production smoke diagnosis and must still pass live production acceptance before claiming resolution.

- In the exact incident fixture, installed Policy contract A and current available compatible Deployment contract B differ; Producer outputs the original single Work without stale `logical_contract`/ref, and native-equivalent resolution chooses B and records it as immutable admission contract.
- A matching A/A revision remains valid and does not cause a false error. Missing, unavailable or incompatible (trust domain, workflow, principal, credential/effect scope, max claims, sharing) revisions fail closed **before Issue creation**. Preserve old Work IDs and any explicitly pinned old Work (outside Producer scope).
- Repeated Producer continuation after successful admission must remain idempotent: same Task/Spec graph, one Issue #530, one Work ID, no paid double dispatch. Normal required CI, review, and existing native queue authorization are not weakened.
