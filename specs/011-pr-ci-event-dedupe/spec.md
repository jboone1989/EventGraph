# 011 · PR CI event scope and review dispatch deduplication

- **Owner direction / evidence**: 2026-10-29 EventGraph [Issue #176](https://github.com/jboone1989/EventGraph/issues/176), T15; the motivation was repeated cancelled checks for #175 and #207 in the inspected Actions window. This document is a **draft until its own PR has been reviewed and approved**; the implementation must pin the accepted Spec revision.
- **Goal**: prevent editing PR metadata and repeat successful checks on the same SHA from generating expensive CI work and redundant central-review dispatch, without weakening Spec-first, independently required reviews, or branch protection.
- **Depends on**: existing `specs/010-ci-change-scope/spec.md` and its docs-only fast path; reuse `scripts/ci/check-spec.mjs` without relaxing its rules.

## Required behavior

1. Keep `edited` in `Check`'s `pull_request` triggers to observe base retargets (`github.event.changes.base`); retargets and ordinary code pushes run the full Check against the latest base. A title/body-only `edited` event may skip the entire `check`, `e2e`, and `docker` jobs **only if** a trusted prior successful Check is verified for the exact **(head SHA, base ref, base SHA)** and current effective diff. Executable diffs require `check`, `e2e`, and `docker` all `success` (never `skipped`); verified docs-only diffs require prior `check` success and trusted docs-only classification, with the existing docs-only e2e/docker skips. Do not treat a newer skipped run, another base, a pending/cancelled/failed run, or missing provenance as prior success. Without proof, execute the normal Check jobs (including the existing docs-only fast path) instead of emitting new skipped successes. `changes` classification always runs. Narrow per-PR `cancel-in-progress` to `synchronize` only so metadata edits cannot cancel running checks. No workflow-level path filters or cross-PR serialization.
2. For a title/body-only `edited` event **with verified prior success under item 1**, `Check` runs only its cheap `changes` classifier; the entire `check` job (including PostgreSQL and its Spec-gate step), `e2e`, and `docker` are skipped. The separately required lightweight **PR metadata / Spec gate** workflow is then the sole Spec validator for the edit, reading the live PR body. Without verified prior success, `Check` runs its existing jobs and Spec gate; the metadata gate also runs. The metadata workflow runs for `opened`, `synchronize`, `reopened`, and `ready_for_review` as well.
3. The lightweight job runs the existing trusted base-branch Spec gate against the live PR head, current target SHA, and current PR description (not a stale event body); no custom Spec implementation or broad dependency installation. Its check must be **required** in active branch rulesets for `develop` and `main` **before** enabling any title/body-only heavy-job skip; until then `Check` keeps its current full behavior. Add `workflow_dispatch` to validate existing open PR heads before relying on the new requirement; a short pending status during rollout is acceptable. Existing required checks and independent review remain mandatory with unchanged names.
4. Deduplicate central-review dispatch only for the exact **(head SHA, base ref, base SHA)**. **Prerequisite, not an existing capability:** EventGraph dispatch must send current base ref/SHA, and the central `livingruntime-remote` reviewer must echo the pair in its `claude-review` commit-status description (a separately reviewed central change, not a copied EventGraph reviewer). Verify the carrier in a real status before enabling dedupe. Suppress dispatch only when a completed successful review explicitly matches the pair; missing/unattributable/pending/failed statuses must not suppress dispatch, even on the same base. Retarget or base advancement changes the pair and requires fresh review despite unchanged head SHA; an old-base status cannot authorize merging. Preserve downstream per-PR idempotency and owner-authorized manual re-review.
5. A base-branch retarget must reclassify the effective diff using the **new base** and run all required heavy checks if that range includes executable changes, even when the PR head SHA did not move. A previous docs-only skipped result must not authorize a merge after retarget. Rapid successive `synchronize` pushes cancel superseded runs for the **same** PR, never a different PR; no global serialization and no new runner pools, databases, bots, or CI framework. Coalescing agent commits before push belongs to the agent's own implementation and is not attempted through arbitrary CI sleeps.

## Acceptance

- AC-1: After verified successful required jobs for the same (head SHA, base ref, base SHA), a title/body-only `edited` event runs the lightweight Spec gate, skips the entire heavy `check`/`e2e`/`docker` jobs, and cancels no in-progress Check. Without verified success, the normal Check jobs execute.
- AC-2: `opened/synchronize/reopened/ready_for_review` trigger the unchanged full Check and the new metadata gate; docs-only PRs keep the established selective behavior.
- AC-3: Changing a valid Spec reference in a PR body to invalid fails the **required** metadata check before merge; restore the valid body and the gate passes.
- AC-4: A repeated successful Check for an already-reviewed exact (head SHA, base ref, base SHA) pair does not redispatch **only after** the central reviewer has echoed that pair in a successful `claude-review` status. A retarget or base advancement forces a fresh review; missing/unattributable status fails closed to dispatch. A new head SHA still dispatches subject to existing PR/HEAD and fork/draft checks.
- AC-5: Different PRs can run full CI concurrently; no workflow- or repository-wide concurrency bottleneck is introduced.
- AC-6: Branch protection still requires existing checks plus the new metadata gate. No merge bypass, production change, or workflow path-filter semantics introduced.
- AC-7: Retargeting a previously docs-only PR to a base where its effective diff contains code triggers fresh `check`, `e2e`, and `docker` plus independent review for the new base before merging; old skipped results and old-base review do not count.
- AC-8: After a failed, cancelled, missing, or unattributable full Check on a code PR, a title/body-only edit cannot turn required failures into skipped successes: it runs the real heavy jobs; a failed-to-skipped bypass regression test must fail against the unsafe implementation.

## Validation

- Reuse the existing Spec-gate tests; add focused tests for any new logic.
- Verify metadata-only edits, base-branch retargets, and synchronize events on test PRs, including a deliberate invalid Spec body edit, a docs-only → executable retarget that produces a fresh heavy Check **and** a fresh review dispatch for the new base, and a pre-existing open PR head reporting the required metadata check after the `workflow_dispatch` rollout path.
- Verify failed-full-Check → metadata edit still runs real heavy jobs, and a previously successful same-pair edit skips the entire PostgreSQL-backed `check` job without duplicating its Spec gate. Verify the central dispatch payload carries base ref/SHA and a real successful `claude-review` status echoes both before enabling dedupe; missing carrier always redispatches. Verify repeated successful run for same reviewed pair vs new SHA/base.
- Update `docs/ci-cd.md` in the implementation PR to describe the metadata gate and review dispatch deduplication; update `.agents/CONSTRAINTS.md` if the named required checks change.
- Independent review required before merging the implementation PR.
