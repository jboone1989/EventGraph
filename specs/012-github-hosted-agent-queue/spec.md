# GitHub-hosted autonomous development queue

**Status:** Draft until this PR has passed independent review and is merged.  
**Date:** 2026-10-30  
**Target repository:** `jboone1989/EventGraph`  
**Target development branch:** `develop`  
**Runtime/control-plane branch:** `main`

## 1. Problem

Development work currently depends on a person repeatedly prompting an agent to continue. A persistent Claude Code session and a host timer do not provide a durable, verifiable task lifecycle. A second hand-built queue would duplicate GitHub's task, workflow, and history capabilities.

The development workflow must be driven by GitHub events and durable GitHub state. It must continue without a ChatGPT conversation remaining open and without code execution on cn-dev, VM13, VM09, or another user-managed host.

## 2. Owner-approved scope

The owner approved the direction in the 2026-10-30 conversation with **“做吧”**, after specifying:

- use GitHub-hosted execution rather than cn-dev;
- prefer existing GitHub capabilities instead of building a parallel scheduler;
- do not retain the previous Pi/systemd-timer/tmux scheduling approach.

This is a development-automation control plane only. It does not replace EventGraph's application runtime queue (PostgreSQL/pg-boss).

## 3. User-visible behavior

1. A repository owner adds the `agent-ready` label to an eligible GitHub Issue. The Issue body must contain a testable task description and acceptance criteria, a pinned Spec reference in the exact form `Spec: specs/<feature>/spec.md@<40-character-commit-sha>`, and the URL of the Spec PR. The Producer verifies that the referenced Spec PR was merged by repository owner `jboone1989` into `develop`, that the pinned Spec commit is an ancestor of current `develop`, and that the Spec file at that commit is unchanged on `develop`. The owner-authored `agent-ready` label event is the task-specific authorization; other actors cannot admit Work.
2. Intake is a deterministic GitHub Actions workflow, not an LLM agent. It validates the owner label event and Issue metadata, builds the native Work JSON, and calls the pinned GH-AW CLI `gh aw work-queue --repo jboone1989/EventGraph submit-work --file <work.json> --worker-profile eventgraph-worker --request-id issue-<number>`. The stable request ID makes duplicate label deliveries idempotent. After successful submission, it invokes `eventgraph-dispatch-gate.yml` on `main` via `workflow_dispatch` once. The Producer job has only `contents: write`, `actions: write`, and `issues: read`: contents permission writes the native queue ledger, and Actions permission dispatches the gate. No custom queue storage or model call is used for intake.
3. The native Dispatcher is a very small GH-AW workflow. It calls `work_queue_dispatch_next` exactly once, requesting at most one Claim and one dispatch. It does not choose a Work ID or worker profile; the native scheduler selects the eligible Work and its approved worker profile. A separate deterministic `eventgraph-dispatch-gate.yml` wrapper checks that no open `agent-work` PR targets `develop` before launching the Dispatcher; it serializes gate runs and invokes `gh aw work-queue --repo jboone1989/EventGraph dispatch eventgraph-dispatcher --wait`. The gate job has only `actions: write`, `contents: write`, and `pull-requests: read`; the native dispatcher/tag path needs Actions and Contents write access. The model-facing Dispatcher remains read-only; only its GH-AW trusted dispatch credential and isolated `dispatch-workflow` safe-output receive the permissions needed to launch the Worker. The CLI's `--wait` waits for the Dispatcher workflow only, not for Worker completion; subsequent dispatches are event-driven as specified below.
4. A GH-AW Worker runs on a GitHub-hosted `ubuntu-latest` runner, checks out EventGraph `develop`, verifies the immutable approved Spec, researches existing code/upstream/official interfaces, implements the task, runs relevant tests, and proposes one non-draft PR targeting `develop`, using an `agent/*` branch and the `agent-work` label.
5. The model-facing Worker has no direct GitHub write permissions. PR creation and Claim completion use GH-AW's claim-scoped safe-output and native Work Queue mechanisms; only the isolated PR safe-output job receives `contents: write` and `pull-requests: write`. Every code Work carries a closed version-1 `effect_contract` and version-1 `resource_scope`. The code Work contract is exactly one repository-scoped `create_pull_request` output with `min: 1` and `max: 1`; its resource scope is the canonical `github.com/jboone1989/EventGraph` repository and repository ID `1416699488`. The Worker PR body includes a machine-readable marker containing the immutable Work ID and originating GH-AW Worker run ID. No other agent-authored write is authorized.
6. A deterministic default-branch `worker-complete` workflow listens for completion of the exact published GH-AW Worker workflow in this repository. It has only `actions: write` and `pull-requests: read` permissions. If a successful Worker run created exactly one open, non-draft `agent-work` PR targeting `develop` whose marker matches that Worker run ID, it reads the live PR head SHA and dispatches Check on that PR branch with `expected_sha` set to that exact SHA. If no matching PR exists and no open `agent-work` PR exists, it invokes `eventgraph-dispatch-gate.yml` once; the queue decides whether a no-write Work or bounded retry is eligible. If any open `agent-work` PR exists without a matching successful Worker marker, the handler blocks further dispatch and surfaces manual recovery rather than creating duplicate work. The helper is deterministic GitHub Actions glue, not a scheduler or LLM agent.
7. The dispatched Check verifies `expected_sha == github.sha`, resolves exactly one current open same-repository PR at that SHA targeting `develop`, and runs Check, E2E and Docker. The existing independent R01–R18 reviewer then reviews that exact SHA. The default-branch `claude-pr-dispatch.yml` forwards completed Check runs for both `pull_request` and validated `workflow_dispatch` events to the central reusable reviewer; when GitHub supplies no PR association for `workflow_dispatch`, the central reviewer resolves the unique live PR by the exact Check SHA. The central reviewer accepts `workflow_dispatch` only after the same exact-SHA/live-PR checks. A stale Check or review cannot authorize a newer SHA.
8. Extend the default-branch `claude-pr-dispatch.yml` with a trusted merge job; the current main copy invokes the central reviewer through the synchronous reusable-workflow job `official-glm-review` and does not merge PRs. Preserve that reusable-workflow call: do not replace it with a fire-and-forget `repository_dispatch` notifier. Add `agent-work-merge` with `needs: [official-glm-review]` and run it only when `needs.official-glm-review.result == 'success'`; this makes the merge job wait until the central review has completed, in addition to requiring successful `claude-review` status for the exact SHA. The main forwarder already forwards all completed Check runs, including validated `workflow_dispatch` runs; preserve that behavior. The stale develop copy must be synchronized to the same reusable-workflow-call structure in the develop-only CI PR. The merge job revalidates the original Check run ID, exact current PR HEAD, open/non-draft state, `develop` base, same-repository head, `agent-work` label, required Check job, successful E2E and Docker jobs for every `agent-work` PR (including docs-only PRs, which deliberately run the full agent-branch validation path), and successful `claude-review` status for that exact SHA. It then requests a normal squash merge with no `--admin`; GitHub branch protection remains authoritative. Its job-level permissions are limited to `actions: write`, `contents: write`, `pull-requests: read`, `issues: read`, and `statuses: read`: Contents permission is for the merge, Actions permission is for the post-merge Check dispatch, and the remaining permissions are read-only verification. If this merge uses `GITHUB_TOKEN`, the same trusted workflow explicitly dispatches Check on `develop` with the exact merge commit SHA as `expected_sha`. Check fails closed if the selected `develop` ref no longer resolves to that SHA. The dispatched Check reruns Check and E2E and re-enters the existing develop `publish` path for that exact SHA; existing VM13 preview and cn-dev worker deployment jobs remain behind their existing `EVENTGRAPH_DEV_AUTO_DEPLOY` gate and run only after successful publish. These are existing application-delivery jobs, not agent execution: GH-AW Workers never run on those hosts.
9. A `resume_queue` job in the develop Check workflow runs with `if: always()` for `develop` push and validated `workflow_dispatch` runs on `develop` only; it has only `actions: write` and `pull-requests: read` permissions. For push runs, the changes detector compares against `github.event.before`. For post-merge `workflow_dispatch` runs on `develop`, the `expected_sha` input must equal `github.sha` and the changes detector compares against the first parent of that exact merge SHA. Agent-branch `workflow_dispatch` runs deliberately set `changes.docs_only == false`, so E2E and Docker run even for docs-only agent PRs. The job requires Check success and accepts either (a) a develop docs-only run where E2E and publish are both explicitly skipped, or (b) a code run where E2E and publish both succeeded. It then confirms the same SHA is still the current `develop` head and no open `agent-work` PR exists, and invokes `eventgraph-dispatch-gate.yml` via `workflow_dispatch` once. The gate performs the open-PR preflight and invokes the native Dispatcher CLI only when no code PR is open. This deliberately handles ordinary docs-only Spec merges: a skipped E2E/publish job must not silently suppress queue continuation. The job does not wait for independent preview/deployment jobs.
10. Queue progression is event-driven: Issue admission submits Work and invokes the dispatch gate; Worker completion invokes the gate when no code PR is open; successful PR merge and develop Check/publish invokes the gate again. The gate has a GitHub Actions concurrency group with `cancel-in-progress: false`; the GH-AW Dispatcher has its own separate concurrency group; and the native Work Queue allows one active Claim per pool. Retry is bounded to `max_attempts: 3`, `backoff_seconds: 1`. No systemd timer, Linux cron, scheduled polling loop, tmux session, or persistent agent process is used. A manual `workflow_dispatch` recovery entry point is allowed.
11. The model endpoint, model ID and key are configuration, not code. Use GLM-5.3 initially, with `GLM_WORKER_MODEL` falling back to `GLM_REVIEW_MODEL` and then `glm-5.3`; use `ANTHROPIC_BASE_URL` from `vars.GLM_BASE_URL` when configured, otherwise `https://open.bigmodel.cn/api/anthropic`. The Worker receives `secrets.GLM_API_KEY` only through the GH-AW Claude engine's documented engine-specific secret binding, never through workflow-level `env` or model-visible prompt text. Changing provider credentials or model ID must not require rewriting queue or Worker logic. The EventGraph default-branch `claude-pr-dispatch.yml` already forwards `GLM_API_KEY` to the central reviewer. Hosted run [#41010390636](https://github.com/jboone1989/EventGraph/actions/runs/41010390636) completed the configured-key check and official Claude Code Action with GLM successfully; this proves the central reviewer key and endpoint work, but not yet the separate GH-AW Worker engine binding.
12. Bound every agentic run by role. The deterministic Producer and event helpers use no model. The Dispatcher has `timeout-minutes: 5`, `jobs.agent.timeout-minutes: 5`, `safe-outputs.timeout-minutes: 2`, `max-turns: 3`, and `max-ai-credits: 5`. Each code Worker has `timeout-minutes: 30`, `jobs.agent.timeout-minutes: 30`, `safe-outputs.timeout-minutes: 10`, `max-turns: 40`, and `max-ai-credits: 50`. Do not disable the credit guardrail. GH-AW AIC is a best-effort estimate, not an exact provider invoice cap; the pinned GLM-5.3 model pricing must be present in the compiled firewall configuration or explicitly configured from the current official Zhipu pricing. If the compiler cannot account for the selected model's pricing, normal intake remains disabled. Report actual token/AIC usage from GH-AW run records and reconcile it with provider billing. Exceeding a turn, credit, or time limit fails the Work visibly; it is not silently retried as success.

### Canonical Work payload contracts

The code Work's immutable payload must use the v1.0.1 field shapes below (task text and Issue/Spec metadata are additional ordinary Work fields):

```json
{
  "task": "Implement the pinned, owner-approved Issue against the pinned Spec.",
  "effect_contract": {
    "version": 1,
    "outputs": [
      { "type": "create_pull_request", "min": 1, "max": 1 }
    ]
  },
  "resource_scope": {
    "version": 1,
    "resources": [
      {
        "host": "github.com",
        "repository": "jboone1989/EventGraph",
        "repository_id": "1416699488"
      }
    ]
  }
}
```

The accepted `effect_contract` is a closed union of exactly two forms:

- No resource effects: `{"kind":"none"}`. This exact form has no `version` or `outputs` fields. A no-write smoke Work omits `resource_scope`.
- Version 1 effects: `{"version":1,"outputs":[...]}`, with only the documented v1 fields. A Work declaring resource effects must also carry a version-1 `resource_scope` with the exact allowed resources.

No extra fields, aliases, wildcards, or mutable post-admission edits are allowed. The native Work Queue validates the contract and checks every delivered resource against the immutable Work scope and installed worker profile.

A no-write smoke Work therefore has this payload shape and no resource scope:

```json
{
  "task": "Verify that a GitHub-hosted Worker can claim, execute and finish a no-write Work.",
  "effect_contract": { "kind": "none" }
}
```

## 5. Acceptance criteria

### A. Queue and dispatch

- [ ] GH-AW source and lock files compile with pinned GH-AW v1.0.1 in strict mode.
- [ ] The deterministic Producer uses the official CLI and no model call; the first accepted submission initializes the native Git-backed Work Queue and Policy on `work-queue`.
- [ ] Producer submission uses a stable Issue-derived request ID; duplicate label events do not create duplicate Work.
- [ ] The deterministic `eventgraph-dispatch-gate.yml` invokes the official `gh aw work-queue --repo jboone1989/EventGraph dispatch eventgraph-dispatcher --wait` command; Producer, worker-complete and resume_queue invoke this gate rather than implementing or selecting Work themselves. Producer, gate, worker-complete, resume_queue and merge jobs use the least-privilege job permissions specified above; write permissions are never granted to the model-facing Worker.
- [ ] The Dispatcher calls native `work_queue_dispatch_next` once and receives at most one Claim; the native scheduler, not the model, selects Work and worker profile.
- [ ] `.github/workflows/aw.json` sets native Work Queue concurrency to one active Claim per pool and bounded retry (`max_attempts: 3`, `backoff_seconds: 1`); Dispatcher workflow concurrency prevents overlapping dispatch runs.
- [ ] Every code Work has the closed version-1 `effect_contract` and immutable version-1 `resource_scope` described above. A no-write smoke Work uses exactly `{"kind":"none"}` and omits `resource_scope`.
- [ ] A no-write Worker completion automatically dispatches the next Dispatcher; a second synthetic Work is admitted and dispatched without a user prompt or external timer.

### B. Real development delivery

- [ ] An Issue is admitted only after the repository owner adds `agent-ready`, and its pinned Spec PR, immutable Spec SHA, and acceptance criteria validate.
- [ ] The Worker runs only on GitHub-hosted infrastructure and checks out `develop`; no user-managed host is contacted by an agent Worker.
- [ ] The Worker creates one PR to `develop` with the exact develop Spec path/SHA, Spec PR URL, Issue authorization evidence, Work ID and Worker run ID marker in its body.
- [ ] `worker-complete` verifies exactly one matching live PR and dispatches Check on its branch with `expected_sha` equal to the live PR head.
- [ ] That dispatched Check validates `expected_sha`, resolves the exact open PR, runs Docker for `agent/*`, and automatically triggers the central independent reviewer; the review is recorded against the same SHA without a manual prompt.
- [ ] A passing `agent-work` PR is squash-merged by `agent-work-merge` only after the synchronous `official-glm-review` reusable-workflow job has completed successfully, the exact-SHA `claude-review` status is successful, the original Check run is still the source of truth, and Check, E2E and Docker have all succeeded. Agent-branch workflow_dispatch runs full E2E/Docker even for docs-only PRs. The merge never bypasses branch protection.
- [ ] After a `GITHUB_TOKEN` merge, the dispatched develop Check validates `expected_sha`, reruns Check/E2E, and produces a successful immutable `publish` run for the exact merge SHA; existing development deployment jobs run only under their existing flag.
- [ ] For a code change, `resume_queue` dispatches the next Dispatcher only after Check/E2E/publish all succeed for the exact current develop SHA.
- [ ] For a docs-only develop merge, `resume_queue` still dispatches after Check success when E2E and publish are explicitly skipped; the changes detector uses the first parent of the validated `expected_sha` for post-merge workflow_dispatch, and the skipped jobs cannot silently strand queued Work.
- [ ] The deterministic dispatch gate refuses to launch another Dispatcher while an `agent-work` PR to `develop` is open; neither worker-complete nor resume_queue bypasses that gate.
- [ ] A manual merge/push to `develop` also resumes the queue through the normal push Check path, including the docs-only path.

### C. Operational behavior

- [ ] No `tasks.json`, `runs.jsonl`, host-side queue, timer, cron, tmux, or long-running agent is required.
- [ ] Queue state, Claims, attempts, delivery and Results can be inspected through the official GH-AW operator CLI and GitHub Actions history.
- [ ] Producer/event helpers use no model. Dispatcher is bounded to 3 turns/5 AIC/5 minutes; each Worker is bounded to 40 turns/50 AIC/30 minutes with a 10-minute safe-output limit.
- [ ] GLM-5.3 pricing is recognized/configured in the compiled firewall; if not, intake remains disabled. Actual token/AIC usage is reported and reconciled against provider billing.
- [ ] The EventGraph-hosted central reviewer has proven `GLM_API_KEY` readability and a successful GLM API call (run #41010390636); the GH-AW Worker engine's separate secret binding is verified by the hosted smoke test.
- [ ] Missing credentials, unsupported API compatibility, queue protocol errors, failed checks, failed review, and budget exhaustion are visible as failures/blocked Work; they are never reported as completed.
- [ ] A real hosted smoke test is required before enabling `agent-ready` intake for normal work: two sequential no-write Work items, then one explicitly owner-authorized code Work that creates a PR and completes the full Check/review/merge/publish/resume cycle.

## 6. Out of scope

- EventGraph product features, its PostgreSQL/pg-boss runtime queue, production deployment, and application architecture.
- Reusing Pi, the old Pi auto-repair flow, VM09/VM13/cn-dev execution, systemd timers, cron, or tmux for agent work.
- Full `develop`→`main` promotion, direct pushes to protected branches, or changing EventGraph's default branch.
- Weakening Spec, Check, E2E, Docker, R01–R18 review, or branch-protection gates.
