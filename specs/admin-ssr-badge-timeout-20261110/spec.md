# Restore admin SSR when today's failed-flow badge queries are slow

**Status:** Draft

## Real VM13 incident
On November 10, 2026, the VM13 `/admin/models` page failed with `web render failed: The render was aborted by the server without a reason` from React server streaming. The deployed `entry.server.tsx` force-aborts after 6 seconds. Direct authenticated diagnostics show `/api/admin/providers` HTTP 200 (~0.55s) and `/api/admin/model-bindings` HTTP 200 (~0.27s), but `/api/admin/nav-counts` may take **13.2 seconds**. The heavy navigation badge is computed by `failedFlowUnitCount() -> currentNewsQueueItems() -> allFlowItemsOverview()`, including daily pg-boss and receipt joins. API/web containers are healthy; this is not a missing model/configuration issue.

## Intended behavior
- An authenticated operator must be able to open **/admin/models**, **/admin/model-bindings**, **/admin/runs** and other admin routes even when the optional badge query is slow or fails. Never bypass authentication, turn private pages into public/cacheable pages, or silently change the underlying news queue.
- Keep `/api/admin/me` authentication gating SSR **before** private page content. Keep `Cache-Control: private, no-store` and existing admin headers. Only navigation badge computation may degrade to **missing**, never fake zero.
- Do not execute the full `failedFlowUnitCount` workload synchronously for **every page visit**. Provide one **coalesced on-demand**, bounded-staleness result in the API process (no new scheduler, cron, queue or database objects). A pending/busy count should not prevent the already available quick `feedback`, `sources` and module counts from returning, or cause repeated parallel full scans. A successful count is kept for at most 30 seconds; after expiration a slow refresh should show no badge until a fresh count is available. Failures are logged and retried no more frequently than a bounded on-demand backoff. Never claim zero counts when the count was not actually calculated.
- Admin SSR streaming for authenticated pages must provide a usable initial shell without waiting for all navigation badges, **including crawler-like user-agent strings**. A slow badge may not trigger a generic full-page SSR abort. Keep the tight 5s streaming timeout for public pages; admin may use a bounded larger deadline for identity/primary loader (e.g. 20s), returning a truthful 503 if the actual main loader fails.
- No extra model writes, worker restarts, requeues, migrations or production deployments. Use the existing Spec review, CI, independent code review, automatic merge to `develop`, and VM13 browser validation.

## Acceptance
1. Browser tests exercise human desktop and iPhone Safari user agents and a bot-like user agent for `/admin/models` and `/admin/model-bindings`. While `nav-counts` is delayed longer than 6 seconds or fails, the main page renders in well under 6 seconds and remains private. The JSON data endpoint and route navigation still work. Failed badge queries do not fabricate 0 or block critical controls.
2. Backend tests prove first request does not await a full 13-second failed-flow count; a concurrent burst starts a single computation, not one per request; a previously returned count is reused only while fresh; a failed count omits `runs` and later requests can recover. An actually measured 0 is distinct from an unavailable count. Avoid wall-clock sleeps in tests using injected clock or controlled promises.
3. The real VM13 live page returns HTTP 200 for `/admin/models`, `/admin/model-bindings`, and `/admin/runs` with a valid admin session, desktop and mobile, no streaming abort or JavaScript errors; check the API route and deployed HEAD digest. Strict existing public page smoke still passes. 
4. Optional nav badges should remain an informative reflection of today's failures after refresh; their absence due to unavailable data is intentionally different from 0. The operational runs page remains the source of truth and preserves its full list and counters.
