# Production release smoke: distinguish genuine hot-ranking data faults from legitimate sparse windows

**Status:** Draft
**Scope:** Existing production release acceptance and hot-ranking diagnostics, not the heat algorithm or end-user publishing rules.
**Incident:** GitHub Actions `release-main.yml` run [42602690058](https://github.com/jboone1989/EventGraph/actions/runs/42602690058), main `fa08c36799638c8d6456a679183361088d8fed3d`, 2026-11-09.

## Observed failure, not an inferred root cause
- The release classifier and immutable digest promotion succeeded; the production SSH action reached the host and downloaded the pinned image. The deployment script advanced the host checkout and reconciled app containers **before** smoke failed.
- After transient connection resets during rollout, page checks were HTTP 200, `/api/site/timeline` had 20 cards, and knowledge stats were episodes 3610 / entities 13356 / relations 26498.
- `/api/site/hot` returned HTTP 200 but `entries: []` in all ten smoke retries. `scripts/production-smoke.py` treats any zero hot entries as a hard failure, so production release ended red; Graphiti release jobs were skipped. This does **not** establish whether ranking refresh is broken, public evidence became invisible, or no stories qualify.
- The actual ranking rules are a 48-hour event window with at least two independent participants and one editorial participant. Recent timeline content does not prove these rules admit even one hot story.

## Product and engineering requirements
1. Preserve those heat/evidence/publication rules. Do not manufacture or seed fake hot entries, disable the scheduler, loosen minimum-participant/editorial thresholds, change the production database schema, or globally mute smoke errors.
2. Implement a **bounded, read-only, production-host diagnosis** invoked through the already deployed app image/Compose API service (no new host dependencies, DB credentials, or custom SQL in Python). Reuse the existing TypeScript backend's `HOT_RULE_VERSION`, `storedHotRanking`, `heatRows`, `sourceClocks`, `behindSources`, and public `latestHotRanking` helpers to report: latest `hot_rankings` `computed_at` and `rule_version`, stored entries and `evidence.candidates`, publicly visible entries, recomputed eligible rows using the actual 48-hour / 2-independent-participant / 1-editorial logic, and source clock freshness. The Python production smoke **consumes only a validated JSON diagnostic produced by the installed backend**; it must not independently reimplement the heat SQL/rules. Never call `computeHotRanking` (it writes), change DB records, log titles, raw articles, credentials or personal data; fail closed on any probe/query/parsing error.
3. Define **fresh ranking** from the existing `apps/worker/src/schedules.ts` `hot.rank` cron `*/5 * * * *`: `0 <= now - computed_at <= 15 minutes` (3 scheduled intervals, measured using UTC timestamps); anything older, in the future, missing, or invalid is stale and a hard failure. Define **fresh source collection** only by existing `sourceClocks()`/`behindSources(clocks, nowMs, true)`: every enabled scheduled RSS/web_list/json_list/x_search source must have `last_ok_at >= now - max(3 * interval_minutes, 90 minutes)` and non-null; the already implemented source-clock rule is authoritative, not a second threshold. If any source is behind, classify the evidence as incomplete and **do not** allow a zero-hot pass; report only aggregate counts, not source details. Also hard fail on unavailable/invalid hot API, unknown or mismatched snapshot `rule_version !== HOT_RULE_VERSION`, current eligible candidates hidden from public view, unavailable/empty timeline, no real news, empty graph, invalid sitemap or environment/security checks.
4. A `200` response with `entries: []` can be accepted **only** when the published snapshot is fresh by requirement 3, its rule version exactly equals `HOT_RULE_VERSION`, the stored entries and numeric `evidence.candidates` are both zero, the backend read-only `heatRows` result filtered by the existing `MIN_PARTICIPANTS=2` and `editorial_participants >= 1` yields **zero** eligible candidates both at `computed_at` and at the current probe time, `behindSources` reports no lagging scheduled sources, and the public read-layer count is zero. Emit `expected sparse window` with measured timestamps/counts. Any inconsistency, unknown rule version, missing candidate metadata, elapsed snapshot staleness, data/clock error, or a qualifying candidate despite zero public entries **fails closed**. Do not alter hot ranking computation, publication filtering or UI.
5. Make main release idempotent following a smoke failure that occurred **after** checkout/image/container changes: verify the exact promoted source and pinned digest rather than assume a failed Action means no live changes. Keep the automatic main release setting and GitHub-native promotion; do not switch off deployment or introduce ad-hoc manual publishing.
6. Add deterministic tests for fresh-empty legitimate window, absent/stale ranking, eligible-but-publicly-hidden entries, stale sources, malformed API, and successful populated hot ranking. Integrate them with existing required Check; keep Docker/E2E/independent review gates.
7. **VM13** is the develop-only Web/API preview host; after implementation merges to develop, its ordinary CI/CD and online browser acceptance must pass, **not** a manual production test. **VM09** is production; the worker must not directly log into or mutate VM09. No new queue, timer, migrations or browser scraping. Use the Spec-first GH-AW native Worker and normal PR auto-merge; validate production only through the existing verified `develop -> main` merge and automatic main release workflow.

## Acceptance evidence
- Operator can tell from release output whether the empty hot list is an expected evidence gap, a stalled ranking, an ingestion issue, or a publication/filtering bug; false-success is prohibited.
- Reproduced incident fixture demonstrates the correct conditional outcome with explicit reasons, not unconditional `count>=1`.
- Exact-HEAD Check/Docker/E2E/independent review pass for implementation; subsequent main release uses immutable digest and existing guarded deployment.
- Do not claim this incident is resolved until a real production smoke passes and any content incident is separately addressed.
