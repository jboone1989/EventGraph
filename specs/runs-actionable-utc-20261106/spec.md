# 运行与积压：只展示当前业务阻塞（2026-11-06）

## 问题与现有复用
现有 `/admin/runs` 同时渲染新闻状态、分组待处理、pg-boss 技术队列、任务时间线和模型路由请求统计。四个后端指标来自不同记录单位，缺少统一解释，不能直接回答“现在多少新闻没做完、什么阻塞、能否恢复”。既有 `currentNews`、`grouping`、`errors`、`receipts`、`jobs` 和操作端点可以复用，不建第二套计数/恢复服务。

## 验收
1. 主屏仅展示按唯一新闻计的待处理/处理中/失败、Worker 在线状态和可操作异常。模型 HTTP 请求成功率、pg-boss 原始任务数、进程个数、80 条任务历史不得充当主屏 KPI。
2. 去重待确认是**新闻分析之后**的独立待办，不得将其误称为失败新闻。汇总数字与可浏览明细必须一一对应；长列表明确分页，不能静默截断为 30。
3. 定时任务“最近失败”仅按当前 UTC 日查询；昨天失败而今天尚未运行的任务不出现在当日异常中。当前未解决的付费回执可跨日保留，但必须明确是待核对事项而非今日失败。
4. “异常与恢复”只呈现需要人工处理或正在阻塞的明细；保留安全的新闻重新处理、未知回执核对和投递处理操作、失败信源链接。移除没有实际业务决策意义的静态队列说明、模型请求统计、队列名称技术清单和历史任务/进程总数。
5. 当前失败新闻总数与可重试范围可能不同（未知付费结果不能自动重试）：两者必须分别明确标注，不将历史回填重复计入新闻总数。当前实时积压按唯一新闻 ID 且互斥统计；已完成内容不受影响。
6. 数据仍每 20 秒刷新；分页、展开保持可用；不改变采集、分析、支付回执、定时任务或 UTC 清理语义。仅面向 develop，生产发布按既有 main 流程。

## 验证
- 验证 30+ 条精选等待时可翻页到最后一条，分页显示的总数等于 API。
- 昨日定时任务失败但今天无运行时，不显示“最近失败”；今天失败仍显示。
- 浏览器验证主屏信息层级与操作按钮、刷新、移动端布局；CI 类型检查和现有自动化测试运行。
