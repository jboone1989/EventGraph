# Auto model routing: balance stage tiers and make the policy visible

**Status:** Draft

## User goal and scope
The operator wants **one-click "自动 · 按流程复杂度"** to actually choose appropriate FREE light, standard, or advanced models per task, instead of sending most traffic to advanced models. Keep the existing router, model registry, successful-candidate cache, per-stage overrides, and the previously approved one-click reset command; **no new router, database migration, provider, background job, or paid fallback**. This is a small, evidence-based reclassification of workflow defaults and their admin presentation.

## Existing behavior and change
- The existing automatic policy `auto` resolves the stage through `stageComplexity`. Its configured tier is a **minimum**; a higher free tier is only a fallback when there is no available eligible model at the requested tier. No silent downgrade below the target and no automatic paid candidates. A provider-declared 429/502/503/504 can switch to the next eligible registered model; timeout/unknown outcome is not replayed.
- Retain light: `prefilter`, `summarize`, `wording`. Retain standard: `score`, `structure`, `translate`, `english`. **Reclassify high-frequency `understand`, `group`, `graphiti` from advanced to standard.** Reclassify `digest` and `explain` from advanced to standard. Keep **`groupReview` advanced** (ambiguous merges receive stronger independent review) and **`report` advanced** (multi-story daily/weekly/monthly synthesis, lower frequency). Unknown future stage keys continue to default to standard, not advanced.
- These are task minimums, not guarantees of quality or of a particular concrete model. Existing manual fixed-model and `auto:light|medium|heavy` per-stage overrides remain authoritative. Existing global settings do not change until the operator saves. Graphiti **embedding** remains a separate fixed embedding model, never routed via the chat tier system.
- The current successful-free-model cache remains useful **within the requested tier**, but may not cause an otherwise available exact-tier model to be bypassed indefinitely by a previously successful higher-tier model. Among eligible models, sort by smallest tier distance first; prefer last successful model **among the same tier**, then existing deterministic tie-breakers. If no exact tier is eligible/available, use higher free tiers; exhausted pool raises existing wait/retry error. Preserve per-model UUID cooldown, same-name multi-connection independence and receipt semantics.

## Admin user journey
1. Open existing `/admin/model-bindings`. The primary default picker offers **"使用部署默认模型"**, **"自动 · 按流程复杂度（推荐）"**, and currently registered compatible fixed chat models. No global `auto:light`, `auto:medium`, or `auto:heavy` as **new selectable choices**; these remain available in the advanced per-stage selector only. For backward compatibility, if a legacy global tier selection is already saved, display that existing selection with a visible "旧全局等级" warning and a clear path to switch to the per-stage automatic policy. The existing backend endpoint still accepts old values; do not silently modify storage.
2. Click the existing **一键应用到全部流程** button. The already approved command saves `models.default=auto` and **atomically clears all prior advanced chat stage bindings**, even if `auto` was already selected. No separate confirmation or new reset UI. Previously saved intentional per-stage overrides can be readded individually afterward; applying the default again clears them again.
3. In the existing advanced workflow table, show an explicit, compact **自动目标等级** for each **active chat stage** using the same backend routing `stageComplexity` table. When the effective choice is `auto`, display the actual tier resolved for that stage; for `auto:tier`, show the explicit tier; for a fixed model, show "固定模型" (no misleading inferred automatic tier); for Graphiti embedding show "独立向量模型". Preserve model/source/action columns, existing table component, mobile wrapping and long model-ID clipping. Do not duplicate the routing tier table in the frontend.
4. Loading/error/empty model list use existing admin states. `auto` remains selectable when no registered chat models exist; successful save is not a claim that a provider is available. Save failure preserves old settings and displays the error. A fixed model choice still validates chat adapter and required vision support.

## Observable acceptance
- Given default `auto` and no manual stage overrides, `understand`, `group`, `graphiti`, `english` and `digest` show **标准** as their actual route tier; `summarize` shows **轻量**, while `groupReview` and `report` show **高级**. A Graphiti embedding row has no chat tier and retains its old binding.
- Given registered light, standard and advanced free models, a light task uses light; standard task uses standard; advanced task uses advanced. A previously successful higher-tier candidate must not outrank a newly available exact-tier candidate. If an exact tier is exhausted, higher free candidates can be used; paid models are never chosen; for standard/advanced tasks there is no downgrade.
- Given one registered free model and one configured paid model, `auto` cannot select the paid model. Given multiple accounts for the same upstream name, their distinct internal model UUIDs remain separate fallback candidates. A known HTTP 429 is eligible for safe failover, while unknown/timeout retains the receipt with no automatic replay.
- Given a global `auto:heavy` previously saved, the default UI identifies it as a legacy global tier and allows switching to `auto` without corrupting it on mere page load. Advanced per-stage tier choices remain available. After applying default, old chat overrides are cleared and the table shows actual `auto` stage tiers; a new manual override changes only that row until the next one-click reset.
- Browser test: default picker excludes fresh global auto-tier choices while advanced stage picker retains them; default apply uses existing bulk endpoint; advanced tier labels reflect server data; mobile layout survives; errors and fixed/embedding display remain correct.
- Backend test: stage map and candidate ordering, last-success within exact tier, escalation to higher free tier, per-model cooldown, no paid selection; admin model-binding JSON uses **the identical stage-tier resolver**, including embedding exception.
- Keep no new columns/tables; the admin JSON contract may add a small per-stage effective tier field, or use an equivalent existing data shape, while old consumers and model CRUD stay compatible. Typecheck, existing Web/E2E/backend tests and independent code review must pass; normal automatic merge to `develop` and VM13 preview validation precede any production release. No operator setting or production queue is modified by deployment itself.

## Deliberate non-goals
No automatic LLM judgment of task difficulty per article; no changes to the number/order of editorial flows, Graphiti ingestion, prompt schemas, news publication, paid-account policy or model ranking metadata. Quality/cost impact must be observed from real receipts after an operator explicitly enables the default policy; do not claim live routing outcomes from unit tests alone.
