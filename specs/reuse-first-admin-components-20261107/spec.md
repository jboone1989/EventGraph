# EventGraph 管理功能开发合同：先写清产品行为，再选择复用方案

**Status:** Draft — awaiting the repository's existing independent Spec Review and owner-delegated automatic approval. This Spec-only PR does not authorize application implementation until merged into develop.
**Target:** develop。沿用现有 Spec → GH-AW Worker → Check/E2E/独立 Review → develop 的流程，不新增调度器、审核 Agent 或 UI 框架。

## 1. 背景与目标

用户反馈：提出“给后台加一个 CRUD”后，AI 常只实现字面上的增删改查，却忽略成熟产品默认应具备的列表可用性、搜索/分页、长字段处理、交互反馈与响应式布局；又反复自行编写已有组件能够提供的基础能力。结果功能需要多轮返工。

**本规范解决两个独立问题，缺一不可：**
1. **需求完整性（What）**：让 Spec 描述清楚产品目标、业务语义、操作流程、普通用户会遇到的状态、非目标与可验证的完成标准；普通 UI/CRUD 常识由项目默认合同补齐，不要求用户每次逐条口述。
2. **复用优先（How）**：在完整 Spec 获得批准后，开发前搜索仓库和成熟组件；只实现现有能力不能满足的业务差异。复用不能代替需求分析，更不能用“接口调用成功”冒充产品完成。

## 2. Research First：develop 已有基础（核查记录）

- `apps/web/app/features/admin/ui.tsx` 包含 `AdminPage`、`DataTable`、`Pager`、`Input`、`Select`、`Button`、`ReasonDialog`。现有 `DataTable` 使用 `min-w-[640px]` 与横向滚动；`Pager` 是独立的分页导航。它们不是自动满足所有质量要求的保证。
- `apps/web/app/features/admin/ProviderConnectionsAdmin.tsx` 复用 `DataTable`，模型列表已实现客户端分页，是可以借鉴的既有产品行为。
- `apps/web/app/components/ui/` 是独立的站点公共组件，不能无根据地把前台风格合并进后台。
- `apps/web/package.json` 为 React 19、React Router 8、Tailwind CSS 4，未安装 TanStack Table 等第三方表格库。只有发现实在的能力缺口后才评估外部选项，例如 https://tanstack.com/table/latest/docs/framework/react/guide/pagination 与 https://ui.shadcn.com/docs/components/radix/data-table 。
- `AGENTS.md`、`.agents/CONSTRAINTS.md`、`source-driven-development`、`docs/spec-review.md` 与 `.github/workflows/check.yml` 已要求先查代码、先审核 Spec，但尚未把**隐性 CRUD 产品常识、Spec 覆盖完整性及复用证据**共同变成稳定的评审标准。本次只增强这些已有入口。

## 3. 每个功能 Spec 必须回答什么（产品合同优先）

对 UI、API、后台管理和工作流功能，Spec 必须有足以让另一个不认识用户的开发者独立完成任务的信息；不强制机械填写无关章节，但不得只写“支持 CRUD / 增加按钮 / 调用 API”。至少覆盖与该功能相关的以下维度：

| 维度 | Spec 应给出的信息 | 审核关注点 |
| --- | --- | --- |
| 目标与范围 | 要解决的实际用户问题、谁使用、在哪个页面/入口完成、什么算成功 | 不能把实现手段（如新增按钮）当成全部用户目标 |
| 数据与业务语义 | 操作对象、标识、关键字段、允许/禁止的状态转移；创建、编辑、删除对关联数据和已有行为的影响 | **删除是硬删还是软删、是否级联**等具有产品后果的选择不得由 AI 自行补字段/迁移 |
| 完整交互 | 用户从进入列表、定位记录、执行操作到看到结果的完整路径；默认值、输入校验、取消/重复操作行为 | 不能仅实现后端路由或“按钮能点” |
| 日常可用性 | 预期数据量、列表浏览方式、需要的搜索/筛选/分页、操作按钮布局、长字段展示、加载/空/失败/成功状态 | 适用的常识应自动补全；不适用时要说明为什么 |
| 视觉与一致性 | 复用本项目既有布局模式；数据密度、关键信息优先级、桌面/移动端展示、极端内容时不遮挡 | 不能允许 UUID 把其他列挤没、按钮把标题挤成竖排 |
| 边界与非目标 | 权限、失败重试或幂等的已有约束、保持不变的模块、明确不需要的新功能 | 禁止自创“暂停原因”、“deleted_at”、第二套队列等未经批准设计 |
| 验收证据 | 对上述每个重要场景写 Given/When/Then 或等价的可观察预期；指定单测/API/浏览器/视觉证据 | “测试通过”“UI 正常”“实现 CRUD”本身不是可验证验收条件 |

**默认机制：** 常规 UI 预期可以由已批准的“管理页面共识”自动继承，Spec 只需明确适用项、例外和具体业务差异。不要求每个页面重复写七页模板，也不要求 3 条固定数据必然分页。对会改变用户数据、权限、支付、删除语义等**实质决策**，若既有项目事实无法确定，必须停在 Spec 阶段明确决策；不能由 Agent 按习惯猜测。

## 4. 管理后台常识：默认继承、可按证据例外

这些是**评审默认要求**而非每个功能无条件强制的功能集：

1. **列表**：主要字段和操作可见；数据量超出单屏/预期持续增长时，使用合理分页或有根据的等价浏览方案；若需要查找指定记录，提供适当搜索/筛选并明确它与分页的关系。不能用假分页掩盖全量客户端加载的真实限制。
2. **长内容与布局**：超长 ID、URL、名称不会挤掉其他核心字段；截断/换行/横向滚动时仍能复制或查看完整值。标题、说明和操作区保持信息层次，不能被不断增长的按钮组挤压。
3. **CRUD 操作**：有明确新增/编辑/删除入口和可辨认的取消/保存结果；保存中不可重复提交；失败能定位原因，成功后列表与计数正确更新；只在业务需要时询问删除确认或原因，不凭空添加冗余输入。
4. **页面状态**：加载中、无数据、请求失败、无匹配搜索结果、记录已变化等状态给出合理反馈，不能呈现假的可点击按钮或沉默失败。
5. **响应式与一致性**：选择现有项目组件和视觉约定；对有 UI 改动的 PR 验证实际桌面和手机视口，涉及多栏操作区时兼顾平板视口。移动端可采用横向滚动或合适的卡片布局，但必须可操作、字段不被无意义挤压。
6. **不过度设计**：短小的固定列表可不分页，不可删除的数据不得强加删除，已有业务行为不得被统一模板覆盖。偏离上述常识时给出基于业务/现有产品的理由。

## 5. Spec Review 的责任（先判产品合同完整，再看实现）

扩展现有独立 `spec-review` 指令，不另起流程：

1. **先检查需求覆盖**：用户目标能否由 Spec 的完整操作流程达成？关键业务选择、边界、成功/失败状态是否明确？常见 CRUD 漏项是否有合理例外？能否据此写出真实测试？
2. **再检查产品合理性**：已有产品约定、同类页面和用户曾明确否定的复杂设计是否被保持？Spec 是否引入未经授权的额外状态、数据库字段或二次系统？
3. **最后检查实现约束**：是否提供 Search/Reuse Before Build 的候选来源和选择理由；是否把某个具体实现写死、妨碍更成熟的复用方案？
4. 出现**会使不同开发 Agent 做出本质不同产品行为的关键歧义**，或遗漏正常用户必经的关键状态，应返回可定位的 FAIL，要求补齐；不要因缺少不相关的 UI 小节而机械拒绝简单修复。
5. Spec 审核不等于代码审核。若关键问题需要产品所有者做业务决定，列出**最小决策点**，不可用 AI 想象的默认选择冒充 owner 批准。

## 6. Reuse Before Build：只有 Spec 过关之后才能选择实现

在具体功能实现中严格依次查看：
1. 现有 EventGraph 完整功能/页面与后台共享组件；
2. 项目已安装依赖的官方 API；
3. 成熟第三方组件/官方推荐实现（仅缺口确凿时）；
4. 仍缺失的少量自定义代码。

维护**一份**可发现的后台功能与组件指南，列出现有组件位置、适用范围、已知限制，以及对列表、表单、操作反馈、分页和布局的复用建议。通过 `AGENTS.md`、`.agents/CONSTRAINTS.md` 与现有 Worker 让 Agent 在动手前读到它；不得平行建设第二套表格/弹窗/审核/队列。

实现 PR 的简短复用记录要回答：查了什么、复用了什么、缺失什么、为什么需要新增代码。一个已有通用组件能直接满足的能力被重新实现，且无具体理由，是独立代码审查的阻断项。

## 7. 验收追踪：从文字到用户可见结果

每项功能 Spec 的重要验收情形应能在实现 PR 中追溯到：**需求/场景 → 代码位置 → 测试或实际操作证据 → PASS / FAIL / UNVERIFIED**。至少包含正常路径、关键边界/错误路径，以及涉及 UI 时的可见操作和视口效果。测试工具与证据类型按风险选择，不能用类型检查证明布局正确，也不能用截图证明删除接口正确。

以下两个示例用于说明完整度，**不是要在本任务实现这些功能**：

**示例 A：用户只说“信源管理加删除”**
- Given 现有信源在列表中，When 点击删除并按既有业务规则确认，Then 该记录从管理列表消失，刷新页面后保持结果；删除失败则保留该记录并显示原因。
- 删除到底硬删除还是软删除、对相关记录与同步任务的影响，应从用户明确要求/已批准业务合同确定；不能自动新增 `deleted_at` 或要求填写“暂停原因”。
- 当信源数较多，用户仍应能查找、分页并操作指定行；长 URL 不应挤掉操作列。

**示例 B：模型管理导入三个 Groq 连接**
- Given 同一厂商有三个不同连接 ID，When 用户在统一选择入口依次选择并导入，Then 每次只向当前连接 ID 发出请求；不得按厂商名称去重。
- Given 连接名称或 ID 很长，When 在桌面与移动端打开模型页面，Then 标题、选择框和主要操作可读且可使用；不能出现标题一字一行。
- 未提供免费目录的厂商应有明确不可用说明，不能假装任意连接都支持同步。

## 8. 本规范的实施边界与验收

实施只限于：
- 一份简短的 `docs/admin-ui-reuse.md`：既是**后台默认产品合同和 Spec 编写检查表**，也是可复用组件地图。避免拆成三套互相矛盾的文档。
- 在 `AGENTS.md`、`.agents/CONSTRAINTS.md` 与现有 GH-AW Worker 加入最少的入口链接和 Spec/Reuse 先后顺序。
- 在**现有** `.github/workflows/check.yml` 的 `spec-review` 和实现独立 Reviewer 中加入相应质量检查；保留原审查结构、状态命名、门禁与自动合并机制。
- 必要的静态/行为回归测试，证明指南与审核入口确实接通；对实际 UI 页面质量，仍应在具体功能 PR 做真实浏览器验收。
- **本任务不重写任何 CRUD 页面，不引入 TanStack/shadcn、不新增表或队列、不增加第二个 Review Agent。**

**本任务的可验证验收：**
1. 仅写“增加 CRUD”但遗漏关键业务语义或用户操作闭环的示例 Spec，现有 Spec Reviewer 能指出具体遗漏；覆盖完整且小范围的示例能通过，不因模板缺章节受罚。
2. 一个实现 PR 若完全满足字面 API 但出现长 UUID 挤压、标题被按钮挤坏或操作反馈缺失，现有独立 Reviewer 能给出可执行阻断理由；若复用已有组件，能识别而非要求再造。
3. 对每个重要验收场景，开发 PR 能提供需求→实现→测试/操作结果对照；无人声称未运行的浏览器验收已通过。
4. 现有 Worker 能找到统一指南并按 **Spec 完整性 → 组件选型 → 最小实施 → 逐条验收** 的顺序执行。
5. 相关静态测试、既有 Check/Docker/E2E 和独立评审真实通过后才能合并；不得仅凭本规范文档宣称任何页面问题已修复。

**Authorization:** 本状态使用仓库现有 Draft → 独立 Spec Review → 自动标记 Owner-approved 的流程；仅当审核通过、Spec PR 合并 develop 后，才由已有 GH-AW 处理 `tasks.md`。Spec PR 本身不改应用/Workflow 代码。
