# Task breakdown — complete product contract, then reuse-first delivery

## Work Items

### T001 — Enforce complete feature Specs and reuse-first admin implementation using existing review/Worker
**Scope:** Establish one concise canonical admin product+reuse guide, then integrate two review stages: (1) Spec review checks product/UX/edge-case completeness and acceptance; (2) Worker and implementation review ensure evidence-backed reuse and traceable delivery. Extend only existing AGENTS/CONSTRAINTS, GH-AW Worker and Check reviewer prompts; no new jobs, agents, UI framework or queue.
**Depends on:** none
**Acceptance:**
- `docs/admin-ui-reuse.md` explicitly starts with a **product contract** for feature Specs (user outcome and entry, CRUD data/meaning, complete user journey, list/search/page choices, states/error feedback, responsive/long data, preservation/non-goals, Given/When/Then acceptance). It gives clear examples of a deficient “add CRUD” Spec and an adequate compact one. Business-significant decisions, such as hard vs. soft deletion or impact on associated data, require an explicit authorized basis, not invented defaults.
- The same guide then maps the current `AdminPage`, `DataTable`, `Pager`, `Select`, `Button`, `ReasonDialog`, etc. to actual `develop` file paths, documents limitations and says when to use an existing feature/installed dependency or investigate a maintained external component. It prohibits gratuitous reimplementation, but does not force pagination where unnecessary.
- The existing `spec-review` prompt in `.github/workflows/check.yml` tests *material* product contract completeness and user-visible acceptance first, before worrying about technical decisions. It flags unclear operation semantics, omitted main states or untestable criteria with a file/line finding; it does not demand a rigid form for every small fix.
- `AGENTS.md`, `.agents/CONSTRAINTS.md` and the current `.github/workflows/eventgraph-worker.md` link the canonical guide. The Worker reads the pinned Spec, checks missing/contradictory product rules, researches reuse, implements only accepted behavior, and records a compact **acceptance → implementation → test/browsing result** matrix and reuse choice in its original implementation PR.
- The existing central implementation reviewer checks the actual PR diff against both the approved Spec and applicable product defaults; demonstrated bad CRUD UX, misleading “working” controls, long IDs crushing columns, omitted meaningful error feedback, or needless duplicate components are actionable blockers. Existing review model/schema, check names and automatic merge contract remain intact.
- Focused tests verify that the two existing reviewer entrypoints and Worker are connected to these rules, and sample scenarios demonstrate that an incomplete CRUD Spec is rejected while a concise but sufficient one is not mechanically blocked. The tests cannot claim to guarantee LLM correctness or actual UI rendering.
- Existing Check/Docker/E2E and independent review must pass; do not claim deployed features or fixed admin pages from this instruction-only task. No extra PRs for the same Work Item.
