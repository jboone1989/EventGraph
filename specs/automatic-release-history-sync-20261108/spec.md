# Eliminate recurring main / develop release-history divergence

**Status:** Draft
**Type:** CI/release-history correctness
**Owner goal:** After every approved release, main and develop must not diverge solely because the release used a merge commit. Do not repeatedly ask the owner to resolve history-only branch conflicts or launch paid reviews for phantom source deletions.

## Evidence (2026-11-08)
- GitHub compare develop...main: 9 main-only commits, 6 develop-only commits, **zero main-only changed files**.
- PR #497 (develop -> main) cannot satisfy main's up-to-date rule while main release merge ancestry is absent from develop.
- PR #498 (main -> develop) has zero GitHub PR changed files but its one-pass reviewer uses `git diff base_SHA head_SHA` (two endpoints, instead of merge-base..head), falsely reports that approved Worker reconciliation, approved Specs and tests are deleted, and fails `claude-review`.
- The develop auto-merge step always uses `gh pr merge --auto --squash` except literal head branch main or upstream import. A new zero-content history-sync branch would lose its ancestry if squashed.
- PR #499 is a safe history-only merge candidate: first parent develop `8ffb3dd`, second parent main `47cf4c3`, tree **identical** to develop `815332e55e46c791efa6d92d75544812da4827a9`. It is intentionally Draft until the review/merge-method handling is corrected.

## Behavior contract
1. Normal feature PRs still flow feature -> develop; the only allowed main application promotion is same-repository develop -> main. Keep all existing Spec, CI, review, immutable-image and deployment gates.
2. An approved develop -> main merge may create main-only **history**. GitHub Actions shall automatically detect this on a main push and, if main isn't already an ancestor of develop, prepare a content-preserving history-sync PR targeting develop. Also provide a manual exact-main-SHA workflow dispatch for **initial reconciliation of the already-existing divergence** after the implementation lands, without waiting for the next release. The history-sync commit has develop as first parent and main as second; its tree is exactly current develop. Never push directly to protected develop, force-push, or create a timer / external controller.
3. Before creating that commit, verify `git diff --quiet $(git merge-base main develop) main`. If main contains any main-only file changes, **fail closed** and report a real change needing review rather than discarding it with an 'ours' merge. Check fresh branch SHAs and do not silently update stale heads. Avoid duplicate sync PRs by deterministic identity or discovery. If develop advances while a sync PR is pending, use the existing GitHub-native non-forced update-branch workflow to incorporate the new develop HEAD. Revalidate against the new **current** develop tip (ancestry + exact tree equality), not the original first parent, and never re-pay a model call for the empty diff. If main advances, close the now-stale history-only PR with an explicit superseded reason and create one new exact-tip sync PR, not an accumulating collection of stale PRs.
4. **All PR code reviews** must inspect GitHub-style `merge-base(base, head)..head` changes, not `base..head` endpoint differences. For a normal PR whose base has not advanced, review behavior is unchanged; for base-advanced PRs, exclude unrelated base-branch changes rather than reporting them as regressions. For a verified history-only PR with zero changed files, skip the model call without claiming to have reviewed any code, and machine-check these invariants against live refs at exact PR HEAD: **(a)** the current develop tip is an ancestor of PR HEAD; **(b)** the current main tip is an ancestor of PR HEAD; **(c)** the PR HEAD tree equals the current develop tip tree; **(d)** main contains zero main-only file changes relative to its merge-base with current develop; **(e)** the original sync commit inside PR HEAD ancestry has first parent = develop tip at creation and second parent = main tip at creation (its original tree equals that original develop tree). A refreshed PR HEAD may itself be a new two-parent merge from GitHub update-branch, so it is NOT required to have the original parents. A successful explicit review-gate result is permitted only if all invariants hold.
5. A verified history-sync PR must be merged through native GitHub **merge commit**, never squash/rebase. Enable `--auto --merge` only after actual required checks and exact-head validation, subject to existing branch rules. No bypass of review/protection; no paid model call for zero-code sync.
6. A verified history-only sync must not trigger production release. If develop's CI is triggered on the merge commit, detect that **its complete file tree is identical to the immediately previous develop HEAD (zero changed files of any kind)**, and skip publishing/deploying an identical application image. Do not alter the publishing semantics of ordinary docs-only or feature merges.
7. After merge, assert `main` is an ancestor of `develop` (until main advances again) and all preexisting develop source/configuration files are unchanged. The next develop -> main release should not need another manual reverse PR. Specifically, once the implementation is merged, close the failed #498 and stale Draft #499, dispatch the new approved sync workflow on exact current main SHA, allow native CI/merge-commit auto-merge, and verify ancestry before resuming blocked promotion #497.

## Acceptance examples
- Given main has only merge-history changes and develop has new approved Worker changes, when release sync runs, it creates a PR with zero source changes; after checks and merge, develop retains Worker source, Specs and tests unchanged, and main is its ancestor.
- Given main contains a real main-only hotfix, when sync runs, it refuses any 'ours' overwrite and reports actionable failure.
- Given a synthetic divergence where endpoint diff shows deletions but `merge-base..head` is empty, reviewer recognizes no code changed and does not call LLM.
- Given a new history-sync PR whose original sync commit does not have validated (develop, main) parents, whose current HEAD does not include both live branch tips, whose HEAD tree differs from current develop, or whose main-only diff is nonempty, no automated merge takes place.
- Given a verified history-only PR merged into develop with an identical file tree to pre-merge develop, when develop CI runs, no application image is built and no preview/production deployment is triggered; the history-only invariant is checked after merge.
- Given a normal feature PR with an unchanged base, its usual squash merge, Spec check and code review behave as before. Given a base-advanced normal PR, code review sees only the GitHub three-dot PR changes.
- Given develop advances while a zero-diff history-sync PR is pending, GitHub native update-branch creates a new PR HEAD with parents (prior PR HEAD, new develop tip); its tree equals **new** develop, it contains live main, and the original initial sync commit is in ancestry. The gate passes on these invariants and merges without force-push or paid review, despite the refreshed HEAD having different direct parents.
- Given main advances while an old history-sync PR is pending, the old PR is closed as superseded and at most one current-tip sync PR is created.
- Given the preexisting Nov 8 divergence, running the manual exact-main-SHA sync after implementation completes reconciles the branches, without waiting for another release.

## Implementation boundaries
Reuse GitHub Actions and gh CLI; no new scheduler, database, service or separate agent. Provide focused offline git-history fixtures and CI tests plus a short branch contract in existing CI docs. Implementation must be on a separate PR after this Spec is approved and merged into develop.
