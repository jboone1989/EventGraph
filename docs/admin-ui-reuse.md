# EventGraph 管理功能开发合同：产品合同与复用地图

> 来源 Spec：[specs/reuse-first-admin-components-20261107/spec.md](../specs/reuse-first-admin-components-20261107/spec.md)（Owner-approved）。
> 这是管理后台与功能开发的**唯一**默认产品合同、Spec 检查表和复用组件地图：Spec 作者、GH-AW Worker、实现与评审都以这一份为准，不平行维护第二套标准。它解决两个独立问题，缺一不可：**先把产品行为写清楚（What）**，**再按证据选择复用（How）**。

## 一、先写清产品行为：功能 Spec 的产品合同

对 UI、API、后台管理和工作流功能，Spec 必须让一个不认识用户的开发者独立完成任务。不强制机械填写无关章节，但**不得只写“支持 CRUD / 增加一个按钮 / 调用 API”**。按适用项覆盖：

| 维度 | Spec 应给出什么 | 审核关注点 |
| --- | --- | --- |
| 目标与范围 | 解决的实际用户问题、谁使用、在哪个页面/入口完成、什么算成功 | 实现手段（如“新增按钮”）不能冒充全部用户目标 |
| 数据与业务语义 | 操作对象、标识、关键字段、允许/禁止的状态转移；创建/编辑/删除对关联数据和已有行为的影响 | 删除是硬删还是软删、是否级联等有产品后果的选择不得由 AI 补字段或迁移 |
| 完整交互 | 从进入列表、定位记录、执行操作到看到结果的完整路径；默认值、输入校验、取消/重复操作 | 不能只实现后端路由或“按钮能点” |
| 列表/搜索/分页 | 预期数据量、浏览方式、需要的搜索/筛选/分页及其相互关系 | 适用常识自动补全；不适用时说明理由 |
| 状态与反馈 | 加载中、无数据、请求失败、无匹配结果、记录已变化等主状态；成功/失败的可感知结果 | 不能呈现假的可点击按钮或沉默失败 |
| 长数据与响应式 | 超长 ID/URL/名称不挤掉核心字段；桌面与手机视口可用 | UUID 不能把其他列挤没，按钮组不能把标题挤成竖排 |
| 边界与非目标 | 权限、幂等/重试的既有约束、保持不变的模块、明确不做的新功能 | 禁止自创“暂停原因”、`deleted_at`、第二套队列等未经批准设计 |
| 验收证据 | 对每个重要场景写 Given/When/Then 或等价可观察预期；指定单测/API/浏览器证据类型 | “测试通过”“UI 正常”“实现 CRUD”本身不是可验证验收条件 |

**有产品后果的决策需要明确授权依据。** 硬删还是软删、是否级联、对关联记录与同步任务的影响、要不要新增字段或状态，必须引用用户明确要求或已批准的业务合同；无法确定时**停在 Spec 阶段列出最小决策点**交给产品所有者，不得按 AI 习惯猜测默认值。仓库先例：信源删除最终确定为软删除（`database/migrations/0126_source_soft_delete.sql`，保留新闻与来源历史，PR #466），确认弹窗**不需要**填写原因——这是讨论后的业务决定，不是实现者的默认选择。

### 两个示例（只说明完整度，不是要实现的功能）

**不合格**：

> 给信源管理加 CRUD：支持新增、编辑、删除信源。

缺失：删除语义（硬/软/级联）没有依据；预期数据量与查找方式未说明；加载/失败/空状态没有任何交代；“实现 CRUD”不是可验收条件。这种 Spec 会让不同开发者做出本质不同的产品行为，应在 Spec Review 被指出具体缺项。

**合格（紧凑即可，不必长篇）**：

> 目标：管理员在 `/admin/sources` 删除错误信源，新闻与来源历史保留。
> 语义：按已批准业务合同软删除（`deleted_at` 置位、停采集，PR #466）；确认弹窗不要求原因。
> 路径：列表（URL `?page=` 分页，每页 100，`FilterChips` 筛选）→ 行内删除 → 确认 → 成功后列表与计数刷新；版本冲突提示刷新，失败保留记录并显示原因。
> 边界：长 URL 截断展示但不挤掉操作列（`DataTable` 横向滚动）；手机视口可操作。
> 验收：Given 列表有信源 X，When 删除并确认，Then X 消失且刷新后仍消失；When 删除失败，Then X 保留且可见失败原因（浏览器操作 + API 测试各一）。

### 默认继承的日常常识（评审默认要求，不是无条件功能集）

1. **列表**：主要字段与操作可见；数据量超出单屏或持续增长时用合理分页或有根据的等价方案；需要定位记录时提供搜索/筛选并说明与分页的关系。不能用假分页掩盖全量客户端加载。
2. **长内容与布局**：超长 ID、URL、名称不挤掉其他核心字段；截断/换行/横向滚动时仍能复制或查看完整值；操作区不被不断增长的按钮组挤压。
3. **CRUD 操作**：有明确入口和可辨认的取消/保存结果；保存中不可重复提交；失败能定位原因；成功后列表与计数正确。只在业务需要时询问确认或原因，不凭空添加冗余输入。
4. **页面状态**：加载、空、失败、无匹配、记录已变化都有合理反馈。
5. **响应式与一致性**：优先复用项目组件与视觉约定；有 UI 改动的 PR 在实际桌面和手机视口验证过；移动端可用横向滚动或卡片布局，但必须可操作。
6. **不过度设计**：短小的固定列表可不分页，不可删除的数据不强加删除，已有行为不被统一模板覆盖。偏离以上默认时给出业务理由。

## 二、再选实现：复用地图（Reuse Before Build，在 Spec 过关之后）

严格按顺序考察：**1)** EventGraph 现有完整功能/页面与后台共享组件 → **2)** 项目已安装依赖的官方 API → **3)** 成熟第三方组件/官方推荐实现（仅当能力缺口确凿）→ **4)** 仍缺失的少量自定义代码。复用不能代替需求分析，也不能用“接口调用成功”冒充产品完成。

### 后台共享组件：`apps/web/app/features/admin/ui.tsx`

| 组件 | 用途 | 已知限制 |
| --- | --- | --- |
| `AdminPage` / `Card` / `Stat` | 页面框架、分区卡片、指标块 | — |
| `Badge` / `Dot` / `Time` / `healthTone` | 状态徽标、健康点、相对时间 | — |
| `DataTable`（含 `Column`） | 通用表格，`min-w-[640px]` + 横向滚动，`dense`/`scrollable` 可选 | 不内置排序/搜索/分页/列宽控制，由调用方组织数据 |
| `Empty` | 空数据占位 | — |
| `Button` / `ButtonLink` | 四种 tone、`busy` 防重复提交 | — |
| `Field` / `Input` / `Textarea` / `Select` | 表单字段与控件 | `Select` 是原生 select，无异步搜索 |
| `FilterChips` | 绑定单个查询参数的筛选 chips | 切换时重置 `page` |
| `Pager` | URL `?page=` 驱动的上一页/下一页 | 只有方向导航（`hasMore`），适合服务端分页 |
| `Json` | 折叠的原始 JSON 查看 | — |
| `ReasonDialog` | 变更前确认/收集原因（`requireReason` 可关）写入审计 | 一次一个动作，不是通用表单弹窗 |
| `KV` | 键值明细列表 | — |

### 可借鉴的完整页面

- `apps/web/app/routes/admin/sources.tsx`：服务端 `?page=` 分页 + `FilterChips` + `Pager` + 删除确认的完整模式。
- `apps/web/app/features/admin/ProviderConnectionsAdmin.tsx`：客户端筛选 + `useState` 分页的页内模式（模型列表）。
- `apps/web/app/routes/admin/audit.tsx`、`feedback.tsx`：分页列表 + 操作反馈。

### 边界与外部选项

- `apps/web/app/components/ui/` 是**前台站点**公共组件；不得无根据把前台风格并入后台。
- 当前未安装第三方表格/组件库（React 19、React Router 8、Tailwind CSS 4、motion）。现有组件确有缺口时，先核对已安装依赖的官方 API，再评估成熟外部选项（如 TanStack Table、shadcn 数据表），并把缺口证据和选型理由写进 `plan.md`；不得为单个页面引入整套 UI 框架。
- 一个已有通用组件能直接满足的能力被重新实现且无具体理由，是独立代码评审的阻断项。

### 实现 PR 必须携带的两份简短记录

1. **复用记录**：查了什么、复用了什么、缺什么、为什么需要新增代码。
2. **验收矩阵**：每条重要验收 → 代码位置 → 测试或实际操作证据（UI 改动含桌面/手机视口）→ PASS / FAIL / UNVERIFIED。证据类型按风险选择：类型检查不能证明布局，截图不能证明删除接口；没跑过的浏览器验收不得写成已通过。

## 三、评审与 Worker 如何使用这份合同

- **Spec Review**（`.github/workflows/check.yml` 的 `spec-review`）：先判产品合同完整性与可测验收，再判产品合理性（未引入未经授权的状态/字段/二次系统），最后判实现约束（是否妨碍更成熟的复用）；不因缺少无关章节机械拒绝小修复。
- **独立实现评审**（`claude-review`）：对照已批准 Spec 与本文默认项检查实际 diff；长 ID 挤压关键列、误导性的“可点但无效”控件、缺失的错误反馈、无理由重复造组件都是可执行阻断项。
- **GH-AW Worker**（`.github/workflows/eventgraph-worker.md`）：按 Spec 完整性 → 复用选型 → 最小实施 → 逐条验收的顺序执行，并在实现 PR 中记录验收矩阵与复用选择。
