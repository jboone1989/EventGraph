## 一、已确认的定位与边界

1. **核心问题**：不满足于离散新闻及实体关联，而要帮助读者理解「世界相较之前改变了什么、事件/过程从何而来、有哪些后续变化、与关注对象有何关系」。用户于 2026-10-26 认可把持续的**态势/过程与状态变化**作为重要研究方向。今天是历史发展的一个切面，而不是彼此孤立的新闻全集。
2. **比喻不是事实模型**：可以借用 Git 分支、分叉、交汇、版本历史来帮助理解，但世界并非 Git 仓库；多个事件指向同一后果不表示它们是同一次事件，也不证明因果。不同解释可以并存，不能强制“合并结论”。
3. **证据边界**：时间先后、共同提及、可核实事实、来源声称的因果、客观依赖、研究假设、市场同步变化必须区分；没有证据就明确未知。保留报道来源、时间、修改、更正与反证。过去的解释不能冒充当时已知的信息。
4. **职责分离**：EventGraph 负责来源、事实、持续变化和公共知识记录；Ferro 或其他作者可以提出竞争性解释和假设，但不得自动升格为已证实关系。面向读者的新闻详情页继续作为独立搜索入口，事件/态势页用于深读；不要因新概念删除新闻页。
5. **复用现有资产**：新闻与事件以 PostgreSQL 的公开事实层为基础，Graphiti/Neo4j 用于实体关系与证据索引；复用已有 MCP、REST、时间回放和关注能力。**不要预设需要第二套图数据库、因果推断引擎、用户账户或独立记忆服务。**
6. **方案不能由模型拍板**：重大产品取舍先研究、独立辩论，再由用户决定；未批准的设想不能写成已定需求。实施仍按既有 [Spec Kit 与审查规则](spec-review.md) 执行。

这些是方向与约束，**不是**对具体事件本体、数据模型、界面或实施优先级的最终批准。

## 二、截至 2026-10-26 的已核实系统现状

- [事件归组](../packages/backend/src/events/group.ts) 与 [关系判断](../packages/backend/src/events/relate.ts)：重点是同次发生及直接进展；候选主要在近 14 天召回，进展优先关联 Story 起始事实，难以自然表达长周期的跨 Story 演化。
- [story_links](../database/migrations/0002_events_reports.sql)：现有 storyline/related 联系不足以独立证明因果，也缺少完整的方向、主张、反证表示。
- [story-route](../packages/backend/src/publication/story-route.ts) 与现有探索/回放是事实与时间线基础，不能被称为完整事件因果网络。
- 已有的 [地区冲突影响追踪规划](../specs/event-impact-tracing/spec.md) 是 **2026-10-25 的规划基线**，不是自动获批的所有功能。它明确区分事实、来源主张、暴露、假设、观测市场变化，并反对无证据连线。与 [编辑政策](editorial-policy.md) 同时阅读。
- 历史上 Claude 在 Remote 主机上的 EventGraph 检出曾落后于远端 develop 100 多个提交，错误声称 Spec 不存在。研究前应核实 GitHub 的最新目标分支与文件；**本地缺失不等于仓库不存在**。

## 三、当前的研究分歧（均非实施决定）

- **Claude Opus 的假设**：事件节点和实体关系之外，还应研究「持续态势/过程 + 可观察状态变量」。新报道是状态变化的证据或站点；面向读者可参考多线路、交汇站的叙事视图。事件间因果解释只是带出处、可能有争议的主张，不是默认连线。
- **ChatGPT 的补充假设**：有证据、有方向的跨 Story 联系和「与我有关」的视角也可能是关键价值，但不能仅凭概念优美就建设通用事件图。
- **共同保留的疑问**：读者真正需要的是线路、状态变化、还是因果路径？如何表示过程、决策、机制和多因素汇聚，避免把可视化的相关误认为因果？哪些「与我有关」的说明能用官方适用范围、公开指标与用户本地关注核实？

**不得因为后一位发言者的总结而抹除另一方意见。** 如果后续证据推翻某个假设，追加带日期的修订与理由，不删除原有分歧的历史。

## 四、先验证、再决定做什么

优先使用真实新闻与原始证据，比较：
1. **理解实验**：同一段历史/现代新闻用普通时间线、态势/状态变化线、事件关系图呈现，测试读者能否正确说明「什么变了、何时变了、哪些关联有证据」；同时测错误因果归因。
2. **联系可发现性**：抽取跨 Story、跨较长时间的真实样本，标注明确的回应/引用/适用范围/因果主张与反证，核对模型候选的漏报、误报和方向错误。
3. **个人相关性**：先用公开适用范围、未来已排期节点及读者本地关注做可解释匹配，不能把尚不确定的个人损益说成确定结果。

实验阈值、样本规模和数据结构需在具体 Spec/方案中讨论，不在本研究档案中臆定。尚未开始以上实验；不宣称有结果。

## 五、跨会话协作协议（无需另造工具）

- **读基线**：产品定位、方案、架构哲学或重要路线讨论开始前，先读取本文件、所引用的有效 Spec 与最新远端代码；只读证据不够就标「未核实」。
- **独立立场**：Opus 优先担任产品/研究的独立反方，Sonnet 主要负责代码质量和实现评审。Opus 应先基于原始材料形成自己的命题、反例、替代解释和可证伪条件，而非照抄 ChatGPT 提供的结论。
- **对照辩论**：分别记录事实、双方主张、反对理由、可验证证据、未决问题。允许不同意，不为达成形式上的一致而附和。
- **用户确认再固化**：只将用户明确认可的产品决定标成「已确定」。新方向、否决与推翻旧判断时，在本文件追加日期、依据及所关联的 Issue/Spec/PR；具体实现要求继续写到现有 specs/，不要把这里当作替代 Spec。
- **保持短而可用**：只存长期决策、争议和指向权威资料的链接；不堆完整聊天记录，不保存密钥，不自动追加未经审核的“模型记忆”。Git 提交和 PR 历史即为版本记录。
