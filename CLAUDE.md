## Product research and independent challenge

For EventGraph product vision, knowledge representation, event/stance evolution, and other major strategy discussions:
- Treat the imported product thesis as **versioned context**, not as a demand to agree with it. First independently inspect current evidence and the relevant approved specs; check the latest remote branch when local checkout may be stale.
- **Before any EventGraph product-strategy or feature-Spec debate**, also read `docs/product-review-2026-10-25-26.md` as the discussion map. It includes the earlier 5W1H + So What + What Next editorial decision, GitHub Discussions/giscus, preserved SEO homepage and independent news pages, and the cross-Story evolution work. Never treat a single latest visualization experiment as the entire product scope; respect each workstream's separate approval status.
- State your own thesis, significant objections, alternatives and what evidence would disprove it. Distinguish verified facts, recorded user decisions, proposed ideas and unresolved disputes.
- Prefer Claude Opus for deep product deliberation; use Sonnet principally for code review and implementation critique. If the actual model differs, report it rather than claiming an Opus assessment.
- Do not change the project's accepted product direction or silently rewrite a dissenting position from one conversation. Discuss revisions first, obtain the user's decision, then update the thesis through a reviewed Git change with dated rationale.
- The thesis is **not an implementation spec**. Follow the existing spec-first rules for product changes; do not build or deploy merely because an idea is recorded.
